Навык для постоянного главного чата `Kodo · Диспетчер задач`. Применяй его, когда поручение — целый проект или крупная фича из нескольких модулей; одну задачу веди навыком `kodo-build-feature`. Все команды — с `--json`; читай `result` ответа и код выхода: 0 — успех, 1 — неверные аргументы или findings, 2 — блокер состояния. Подробности: `docs/BLUEPRINT.md`, `docs/T3-HOST.md`, `docs/PROJECTS.md`.

## 0. CLI

1. Проверь возможность, а не номер версии: `kodo project --help --json` (или локальный `node "<абсолютный путь к Kodo>/cli/index.mjs" project --help --json`) должен завершиться с кодом 0 и `result.status: "help"`. Так отвечает только CLI, который выдаёт брифы с собственным префиксом; 0.2.6 не знает `project`, а 1.0.0 отвечает `project_arguments`.
2. Проверка не прошла — используй локальный `node "<…>/cli/index.mjs"`, если он её проходит; иначе скажи пользователю обновить Kodo и не продолжай с устаревшим CLI.
3. Дальше `kodo` в этом навыке — выбранный CLI. Ответы `next-wave` дают его префикс в `result.cli`, а команды в брифах (`selfCheck`, `completeCommand`, `abandonCommand`) и в поле `command` элементов `result.commands` (ответы `bootstrap`, `apply-spec`, `extend --prepare`) уже вызывают тот же пакет: `node "<абсолютный путь к cli/index.mjs>" …`. Готовые команды выполняй из этих полей с исходным префиксом. Для отдельной команды `project gates` используй тот же `result.cli`; `result.next` — пояснения для чтения, строку оттуда оболочке не передавай, а `why` объясняет, когда нужна команда. `--json` добавляй только к `completeCommand` и `abandonCommand`: в `selfCheck` и `result.commands[].command` он уже есть, повтор флага парсер отклоняет. `project_path_unsafe` — в пути проекта, Kodo home или `KODO_WORKTREE_HOME` есть символы, которые оболочка раскрыла бы (`$`, `` ` ``, `%`, `!`, кавычки), либо это сетевой путь, корень диска или путь без буквы диска: попроси пользователя переименовать каталог или перенести проект в подкаталог локального диска. Справка: `kodo project --help`, `kodo project <действие> --help`.

## 1. Чертёж проекта

1. `kodo project bootstrap "<идея пользователя>" --root <абсолютный корень> --prepare --client <codex|claude-code> --json` — `--client` задаёт клиент гейтов в шаблоне `kodo.config.json` (только подписка Claude Code — `claude-code`). Каталог `--root` должен существовать: для нового проекта сначала создай папку (иначе exit 1 и `result.reason: "bootstrap_root_missing"`). Репозиторий не меняется. Прочитай все файлы пакета из `result.bundle.dir` (контекст, правила, шаблоны) и шаги `result.next`. Известные секреты, PEM-ключи и похожие на учётные данные значения в пакете заменены на `[REDACTED]`; `result.summary.redacted: true` — скажи пользователю, что в метаданных репозитория были такие значения (самих значений не показывай). Отказ `bootstrap_context_unsafe` приходит в `result.reason` (`result.code` — `project_invalid`), как и другие коды `bootstrap_*`: безопасно отредактировать не удалось, пакет не создан — покажи код пользователю.
2. Напиши чертёж в `<root>/.kodo/blueprint/` сам, текущей моделью:
   - `PROJECT.md` с непустыми разделами «Цель», «Модули», «Стек», «Критерии готовности»; карта модулей — какие каталоги принадлежат какому модулю.
   - `interfaces/<module>.md` — замороженные контракты между модулями (имя файла — slug модуля).
   - `spec.json` — ProjectSpec v1 с `"execution": {"cadence": "wave", "integration": "branch"}` и `root`, равным корню проекта.
   - Волна 0 — эпик или майлстоун `foundation`: каркас, линтеры, стенд тестов, общие интерфейсы. Каждая задача вне Волны 0 транзитивно зависит от её задачи; задачи Волны 0 не зависят от остальных. Первая задача Волны 0 создаёт минимальный проходящий тест (его путь — в её `writePaths`): прогон `node --test` без тестов — отказ проверки (`fast_check_no_tests`). Для многомодульных Rust-проектов (единый Cargo workspace с ≥ 3 крейтами) Волна 0 обязана содержать задачу, которая: создаёт корневой `Cargo.toml` с `members = ["crates/*"]` и `[workspace.dependencies]` с заранее перечисленными внешними крейтами, компилируемый контрактный крейт (`Cargo.toml` и `src/**` в `crates/<name>-contracts` или в крейте, явно объявленном строкой `contractCrate: crates/<name>` в `PROJECT.md`), заготовки всех крейтов карты модулей (`Cargo.toml` и `src/lib.rs` с заглушкой), коммитит `Cargo.lock` и `.gitignore` с `target/`, а также записывает `architecture.policy.json` (`schemaVersion: 2, language: "rust"`, также в её `writePaths`), в `layers` которой заранее внесены все крейты карты модулей, а в `allowedExternalCrates`/`allowedDevExternalCrates` — нужные внешние крейты (иначе задачи Волны 1+ получат `ownership.unowned` или отказ по зависимостям, а менять политику им запрещено). Задачи Волн 1+ наполняют `src/` своих крейтов; новая внешняя зависимость добавляется отдельной задачей-интегратором, у которой в `writePaths` указаны корневой `Cargo.toml`, `Cargo.toml` крейта-потребителя (для добавления `dep.workspace = true`), `Cargo.lock` и `architecture.policy.json`. Обычным задачам нельзя накрывать контрактный крейт широкой маской (`crates/**` → `contract_scope_too_broad`), а без задачи контрактного крейта `apply-spec` вернёт `contract_crate_required`.
   - Задачи без пути по `dependsOn` идут параллельно: их `writePaths` не пересекаются (ни равенства, ни вложенности, ни glob-перекрытия).
   - Граф эпиков ацикличен: если задача эпика X зависит от задачи эпика Y, никакая задача Y не зависит (через задачи любых эпиков) от задач X.
   - `owner` каждой задачи — роль: `architect`, `developer`, `ui-qa`, `performance`, `security`, `reviewer`. Хвостовую задачу `reviewer` в эпик не добавляй: ревью делает гейт эпика, а лишняя задача — ещё одна волна и чат. У задачи — проверяемые `acceptance` и ссылки `interfaceRefs` вида `{"kind": "interface", "path": "interfaces/<module>.md"}`.
3. Покажи пользователю карту модулей, Волну 0 и порядок волн коротким списком до регистрации.
4. Подготовь `kodo.config.json` и Git. Создай `<root>/kodo.config.json` по `templates/kodo.config.json` пакета: `client` — подписочный клиент, который исполняет гейты (`codex` или `claude-code`; есть только подписка Claude Code — `claude-code`), `commands.test` — команда тестов выбранного стека (шаблон заполнен по найденному стеку; другой стек или `commands.test: []` в шаблоне — задай сам, правила в `rules.md`). Для многомодульных проектов с `architecture.policy.json` (включая Rust workspace) сразу включи в `kodo.config.json` `"architecture": {"enabled": true}` (иначе архитектурный гейт остаётся `disabled`, и защита контрактов молча не работает; на Волне 0 с нуля без `Cargo.toml` и политики на базе гейт корректно проверяет голову). Файл уже есть — проверь в нём эти поля, остальное не перезаписывай. Проверка волн берётся из закоммиченного файла, поэтому он входит в коммит исходного состояния до регистрации; без него `apply-spec` отвечает finding `blueprint_config_missing`. `root` — корень Git-репозитория (не подкаталог), в нём есть хотя бы один коммит, а всё вне `.kodo/blueprint/` закоммичено или в `.gitignore`. Пустой каталог — `git init` и первый коммит исходного состояния; в существующем репозитории пользователя коммить только с его согласия.
5. Выполни команду `apply-spec` из `result.commands[].command` ответа bootstrap. Сохрани её целиком: при повторе регистрации используй тот же `--command-id`.
   - Exit 1 и `result.code: "blueprint_findings"` — исправь чертёж по каждому `findings[].code` и повтори. `split_required` — раздроби перечисленные задачи на меньшие с отдельными `writePaths` и зависимостями; `blueprint_parallel_overlap` — разведи пути пары или добавь зависимость; `blueprint_epic_cycle` — перенеси задачи между перечисленными эпиками или объедини их; `contract_crate_required` — добавь в Волну 0 задачу создания компилируемого контрактного крейта (`Cargo.toml` и `src/**` в `crates/<name>-contracts` или в крейте, объявленном строкой `contractCrate: crates/<name>` в `PROJECT.md`) и включи `architecture.policy.json` в её `writePaths`; `architecture_policy_required` / `architecture_policy_order` — включи `architecture.policy.json` в `writePaths` задачи Волны 0 и поставь остальные задачи Волны 0 в зависимость от неё; `contract_scope_too_broad` — сузь `writePaths` перечисленных задач, чтобы они не накрывали контрактный крейт широкой маской; `blueprint_git_required` и `blueprint_config_missing` — выполни шаг 4.
   - Успех: сохрани `projectId`; `result.modules` — майлстоуны, эпики и `waveZero`.
6. Выполни нужные команды `result.commands` из ответа `apply-spec` по их `why`: перед первой волной установи управляемый oxlint для самопроверки воркеров (команда `tools install oxlint`, один раз на машину, нужна сеть; для TypeScript-проекта ещё команда `tools install typescript`), затем первая волна. Установку делаешь ты, не воркер. Успех самопроверки — `feedback_ready`; `blocked` в `ci feedback` воркера из-за отсутствующего инструмента — не успех: установи инструмент и попроси воркера повторить самопроверку в том же чате.

После создания проекта пользователь называет доступные подписки (провайдер, модель, слоты и тир) и машины (тип, число воркеров, предел тяжёлых сборок, при наличии ID окружения). Сохрани согласованный профиль вне Git и выполни `kodo project profile set <projectId> --file <путь>`. Формат приведён в [RUNTIME](../../docs/RUNTIME.md#профиль-исполнения-волн). Если пользователь работает без профиля, используй прежний максимум 5.

## 2. Цикл волн в T3

При назначении нового брифа учитывай его `subscription` и `machine`. Запрашивай новые задачи после каждой интеграции, пока остальные чаты работают.

1. `kodo project next-wave <projectId> --host t3 --limit <N> --json`. `project_busy` при короткой гонке с резервом или приёмкой гейта — повтори `next-wave` после записи состояния. Exit 2 с пустыми `briefs` — свободных задач нет: обработай идущих делегатов, а если их нет — проверь отложенные гейты по шагу 7 и разбери `blocked`, где каждая строка называет причину. `project_retry_required` — попытка брошена: шаг 3 (`--retry-failed`). Строка гейта (`kind`, `id`, `gateId`, `runId`) — гейт остановлен: шаг 7; `project_gate_pending` — выполни `kodo project gates <projectId> --json`. `project_task_failed`, `project_task_blocked`, `project_epic_<состояние>`, `project_milestone_<состояние>` (`kind`, `id`) — остановлена сама задача, эпик или майлстоун: покажи пользователю. `project_dependency_cancelled` — задаче нужна отменённая задача `dependencyId`, сама она не начнётся: покажи пользователю. `project_risk_unapproved` и прочие коды тоже покажи пользователю (одобрение риска `kodo project approve-risk` — только его решение). `result.code` `project_accepted` или `project_released` — проект принят (или выпущен): цикл волн закончен, переходи к разделу 3. Повтор возвращает и брифы уже идущих попыток (с тем же `attemptId`): новых попыток для них не создаёт, но и не говорит, назначены ли они.
2. Один раз за сессию вызови `orchestrator_capabilities`, если ещё не вызывал.
3. Веди журнал назначений `brief.attemptId → taskId и childThreadId делегата`. После каждого `delegate_task` запиши строку `назначено <taskId задачи> <attemptId> → <taskId делегата> <childThreadId>` (оба id — из ответа `delegate_task`) в свой ответ в этом чате (история чата сохраняется) и держи таблицу в памяти сессии. После архивации дописывай `архивирован <attemptId> <childThreadId>`. В репозиторий проекта журнал не пиши.
   - Бриф, чей `attemptId` уже есть в журнале, назначен: `delegate_task` не вызывай, жди уведомления его чата. Иначе два чата будут писать в один worktree.
   - После перезапуска диспетчера (новая сессия, сжатие контекста) восстанови журнал из истории этого чата и один раз сверь сохранённые чаты: `t3_thread_list` с `titleContains: brief.chatTitle` и `includeSubagents: true` — статус чата и его id (это `childThreadId`); для завершённого чата вызови `t3_thread_read` с `threadId: <childThreadId>` и прочитай полный SHA из последнего отчёта именно этой попытки. Это разовая сверка, не цикл опроса. Идущий чат — жди уведомления; завершённый с SHA — шаг 5.
   - Бриф, для которого журнал или чат найти не удалось, всё равно считай назначенным: второй чат не создавай, покажи пользователю `taskId` и `attemptId`.
   - Переназначение — только `brief.abandonCommand` этой попытки с подстановкой `<SHA>` (последний SHA из отчёта воркера, если его нет — `brief.baseSha`) и `--json`, затем архивация чата этой попытки (шаг 6) и `next-wave ... --retry-failed`: новая попытка получает новый `attemptId`, и для неё создаётся новый чат. Без `--head` или `--attempt` команда отказывает `project_arguments`; отказ без `--attempt` мог бы остановить чужую (новую) попытку.
4. `delegate_task` — только для брифов без записи в журнале, по одному на бриф:
   - `title: brief.chatTitle`, `isolation: "shared"`, `role: "implementation"`; второй worktree не создавай — он уже есть в `brief.worktree`.
   - `task`: `brief.prompt`, затем `brief.roleInstructions`, затем требования: работать строго в абсолютном пути `brief.worktree` и только в `brief.writePaths`; читать интерфейсы из `brief.interfaces`; выполнить `brief.selfCheck` и исправить найденное; закоммитить в `brief.branch` без push, PR, merge и rebase; не запускать других агентов; закончить с чистым worktree и последней строкой вернуть полный SHA коммита.
   - Без секретов, токенов и приватных конфигураций в `task`.
5. Жди уведомлений о завершении делегатов по правилам хоста, без циклов опроса. По каждому завершению выполни `brief.completeCommand` с подстановкой полного SHA и добавь `--json`. В команде уже есть `--attempt <attemptId> --defer-gate`.
   - `integrated` — задача влита в `kodo/project/<projectId>`; сразу архивируй чат этой попытки (шаг 6) и запланируй отдельный проход гейтов (шаг 7).
   - `checks_failed` — передай `result.code` и `result.message` в тот же воркер-чат: `t3_thread_send` с `threadId: <childThreadId>` (тот же worktree, новый чат не создавай). Отправка в завершённый чат начинает в нём новую задачу и возвращает её `taskId`: допиши его в строку журнала этой попытки и жди уведомления, как после `delegate_task`. Затем повтори `complete-task` с новым SHA. Если исправление невозможно — `brief.abandonCommand` с подстановкой SHA и `--json`; ответ `abandoned` — сразу архивируй чат (шаг 6), затем `next-wave ... --retry-failed` (шаг 3).
   - `abandoned` — попытка остановлена: сразу архивируй её чат (шаг 6).
   - `blocked` с `project_integration_conflict` — проверенный коммит не сливается с текущей головой интеграционной ветки, rebase протокол не поддерживает: `brief.abandonCommand` этой попытки (с `--attempt`) с подстановкой SHA и `--json`, затем сразу архивируй её чат по `childThreadId` (шаг 6) и `next-wave ... --retry-failed` — новая попытка от новой головы получит новый чат.
   - Другой `blocked` — покажи код пользователю; `project_busy` — другой контроллер держит проект, повтори позже.
   - `blocked` с `project_control_blocked`, `project_cancelled` или `project_lease_lost` и полем `result.integration` после интеграции — слияние уже сделано, гейты не прошли (`gates` остался `null`). Покажи код пользователю; после снятия паузы (восстановления проекта) повтори ту же `complete-task` без `--defer-gate` или вызови `kodo project gates <projectId> --json`: гейты запустятся один раз. `project_integration_queue_timeout` — строка осталась в очереди, повтори ту же сдачу; `project_submission_stale` — сдача устарела (другая попытка, другой head или отказ), не повторяй её, смотри следующий `next-wave`.
6. Архивация воркер-чата — сразу, как `complete-task` вернул итог его задачи (`integrated`, в том числе повтор с `replayed: true` для уже принятой гейтом задачи, или `abandoned`), не в конце проекта: `t3_thread_organize` с `action: "archive"` и `threadId: <childThreadId>` из журнала. Архивируй только чаты из своего журнала; диспетчер и чужие чаты не трогай, базы клиента не правь. Архив сохраняет историю, это не удаление. Ответ `thread_not_found` — чат уже убран: запиши `архивирован <attemptId> <childThreadId> (thread_not_found)` и продолжай. Не останавливай идущий чат `t3_thread_interrupt`: ненужного делегата останавливает `task_cancel`.
7. За гейты отвечает диспетчер. После `integrated` запусти выбранным CLI отдельную команду `kodo project gates <projectId> --json`. Используй сеанс команды с возвратом управления главному чату и сохрани его идентификатор до получения JSON и кода выхода. Пока идут проверки и ревью, принимай результаты соседей и выдавай следующие брифы. Один проход на проект: если за это время приняты новые сдачи, после завершения прохода вызови команду ещё раз. При краткой занятости проекта на этапе записи повтори команду после завершения конкурирующей операции.
   - После перезапуска подхвати сохранённый сеанс. Если его итог потерян, выполни обычный `project gates <projectId> --json`. Пустая волна без активных воркеров тоже требует такого прохода перед остановкой: готовые гейты восстанавливаются из состояния проекта.
   - `passed` — проверь `project status`. При `accepted` переходи к доставке. Иначе запроси `next-wave`. Если проход ничего не принял и задач или активных чатов нет, посмотри `kodo report --project <projectId> --json` и сообщи блокер.
   - При `blocked` сначала покажи `result.code`, если он есть (пауза, отмена проекта или команды), затем строки `result.gates?.blocked`, если они есть: при остановке до запуска гейтов `result.gates` нет. Строка со `stage: "install"` (`gate_invalid`: gate Run ещё не создан, `runId` в ней только зарезервирован) или без `runId` (`wave_project_head_mismatch`) — `kodo status` не вызывай, покажи её `code`, `stage` и `message`. Иначе — gate Run: `kodo status <runId> --json` с `runId` этой строки; `blocker.current` (`code`, `message`), упавшие проверки `checks.results[]` с `exitCode` ≠ 0 (`kind`, хвост `output`) и `review.findings` — только если ревью дошло до конца (при провале проверок `review: null`). Гейт не повторяется сам.
   - Если Run в `waiting_limits`, дождись восстановления лимита и продолжи тот же Run обычной командой `gates`. Для Run в `blocked`, `failed` или `cancelled` после устранения причины (например, восстановления окружения или подписочного клиента) запусти `kodo project gates <projectId> --retry-failed --json`. Если ремонт gate Run конфликтует с уже влитой соседней задачей (`project_integration_conflict`), выполни этот явный повтор на обновлённой голове. Новый гейт проверяет текущую интеграционную голову и может выполнить ограниченный ремонт в путях покрытых задач. Для уже интегрированной задачи `--abandon` и `next-wave --retry-failed` новую попытку не создадут. Если нужен отдельный патч, с которым ремонт гейта не справился, оставь проект заблокированным и передай причину пользователю. Добавление майлстоуна доступно только после приёмки или выпуска.
8. Повторяй шаги 1–7, пока `kodo report --project <projectId> --json` не покажет `status` `accepted` или `released` (цикл закончен) или блокер из `blockers[]` (`taskId`, `runId`, `code`, `scope`), который нужно показать пользователю. `kodo project status <projectId> --json` даёт те же `blockers`.

Принятие (`accepted`) даёт только gate Run эпика, майлстоуна или проекта. Не помечай задачи принятыми сам и не обходи проверки.

## 3. После приёмки

1. Воркер-чаты уже архивированы по ходу волн (шаг 6 цикла). Сверь журнал: назначение без отметки `архивирован` — архивируй сейчас по тому же правилу.
2. Доставь принятый SHA из `kodo/project/<projectId>` в целевую ветку пользователя. Сверь SHA ветки с проверенной головой итогового гейта. Для локальной доставки в чистом checkout целевой ветки выполни `git merge --ff-only <принятый-SHA>`, если это разрешено правилами проекта. При расхождении историй или защищённой ветке создай ветку доставки от принятого SHA и проведи обычный PR с актуальными проверками. Интеграционная ветка остаётся открыта только в служебном worktree Kodo. Проверь результат доставки в целевой ветке по правилам проекта.
3. Покажи пользователю `kodo report --project <projectId>`: принятые эпики, проверки, блокеры. Если установленная версия Kodo этой команды не знает, покажи `kodo project status <projectId> --json`.

## Без T3

`kodo project drain <projectId> --concurrency <N> --json` исполняет волны нативными сессиями Kodo до `accepted` или блокера. Pull-команды во время идущего `drain` отвечают `project_busy`.

## Новая фича в готовый проект

1. `kodo project extend <projectId> "<фича>" --prepare --json`; прочитай пакет и шаблон `result.template`. Фича добавляется только в принятый волновой проект (`accepted`/`released`, не на паузе, без идущих попыток): иначе exit 2 и `result.reason: "project_append_blocked"` до пакета — сначала доведи текущие волны до приёмки или сними паузу.
2. Запиши майлстоун в `<result.bundle.dir>/milestone.json`: новый майлстоун, его эпики, 1–6 задач; зависимости — только на новые или уже принятые задачи; `writePaths` не пересекаются с параллельными и незакрытыми задачами. У задачи `interfaceRefs: []` или полные Ref, скопированные без изменений из раздела «Привязанные интерфейсы» `context.md` (тогда воркер получит контракт в брифе); короткая форма `interfaces/<module>.md`, изменённый или неизвестный Ref и Ref с непроверяемым evidence — finding `milestone_interface_unbound`: новые ссылки привязывает только `apply-spec`. Хвостовую задачу `reviewer` не добавляй.
3. Выполни `result.commands[].command` ответа `extend --prepare` — это `append-milestone <projectId> --file "<путь к milestone.json>" --command-id <UUID> --json`. Для повтора сохрани UUID из выданной команды. Если ответ потерян и CLI сообщает о совпадении ID майлстоуна, сверь добавленные задачи и эпики со снимком проекта. Findings по содержимому — исправь файл и повтори. Прежние майлстоуны, эпики и задачи не меняются; проект снова `running`.
4. Дальше — тот же цикл волн.

## Правила

- GPT и Claude — только через подписочные клиенты, без API и fallback на API.
- Секреты не попадают в чертёж, брифы, поручения и отчёты.
- Один `attemptId` — один воркер-чат; новый чат — только для новой попытки после `--abandon` и `next-wave --retry-failed`.
- Воркеры коммитят только в свой `brief.worktree` и свою ветку и не запускают других агентов; доставку (push, PR, merge, release) выполняет координатор по своим правилам, не воркеры.
- Блокеры, отказы проверок и решения, меняющие объём, показывай пользователю, а не скрывай повторами.
