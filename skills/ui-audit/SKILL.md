---
name: ui-audit
description: Проверяй существующий интерфейс по пользовательскому сценарию, скриншотам или доступному приложению. Находи проблемы взаимодействия, состояний и доступности.
---

Выбери сценарий из задачи: кто пользователь, что он пытается сделать, откуда начинает и какое состояние означает успех. Пройди его в доступном интерфейсе. Для значимых проблем сохрани экран или точные шаги воспроизведения.

В запуске Kodo учитывай `uiVerification` и переданный stage tool context: координатор владеет установкой, процессами и live-проверкой, рабочий агент готовит scoped сценарии и анализирует безопасные квитанции. Для web доступны Browser Harness, Chrome DevTools MCP, Browser Use, Vibetest и Jev Ultrafast; для выбранного app/window — Agent Desktop. Не выбирай инструмент только по наличию пакета. Browser Use/Vibetest/Jev требуют Google, Jev также TypeSafe; ключи остаются у координатора, GPT/Claude — только подписочные клиенты.

Зафиксируй независимые DOM/accessibility assertions, а не только goal или ответ модели DONE. Включённая проверка должна пройти все cases в настроенных maxSteps/timeoutMs; ошибка, missing credentials/tool, ambiguity или malformed output не являются PASS. `disabled` имеет `passed:null` и требует явного указания. Используй собственные endpoint/профили; запись выключена, evidence приватно вне Git. После uncertain desktop click проверь свежий scoped readback, не повторяй действие вслепую. Не используй личный браузер при сбое инструмента.

Проверь основной путь и относящиеся к нему состояния: загрузка, пустой результат, ошибка, повторная попытка, узкий экран, управление клавиатурой и видимый фокус. Не выполняй реальные покупки, отправку сообщений или иные внешние действия, если они не входят в поручение.

Если доступны только макет или исходники, отдели замечания по ним от поведения, проверенного в приложении. Не заявляй соответствие стандарту доступности на основании одного экрана.

Для каждой проблемы опиши место, сценарий, влияние и конкретное исправление. Отдай сначала препятствия выполнению задачи, затем проблемы читаемости и визуальной иерархии. Избегай редизайна без связи с целью пользователя. При запросе только на аудит не меняй файлы.

Свяжи вывод с проверенным head/config/pins и evidence. Найденную exploratory QA ошибку проверь в самом приложении, исправь причину и повтори сценарий; не удаляй находку ради зелёного отчёта. Разделяй fixture/локальные тесты, реальный UI, проверку пакета и deployment. Playwright MCP остаётся совместимым отдельным клиентским инструментом; шаблон MCP не подтверждает живое соединение.
