description: Выполняй порученную разработку через Kodo с анализом Gemini, планом текущей модели, исполнителями, проверками и настроенной доставкой.
---

Используй установленный `kodo` или доступный локальный `cli/index.mjs`. Прочитай инструкции проекта. Не подменяй запуск Kodo самостоятельным выполнением всех этапов без сохранённого runId.

Сохраняй постоянный чат приёма задач `Kodo · Диспетчер задач` активным. Если host-клиент поддерживает видимые worker-чаты, координатор через его app tools поручает реальную scoped работу в понятно названных чатах проекта, например `Kodo · QA безопасности` или `Kodo · Документация UI`. Чат должен выполнять поручение и возвращать проверяемый результат, а не копировать логи. В доступном Codex desktop workflow используются `create_thread`, `wait_threads`, `set_thread_archived`; не дублируй одну запись одновременно разным исполнителям. Привязывай write scope, артефакты и результаты к существующему runId.

После проверки завершения архивируй только созданные для этой работы worker-чаты штатным механизмом клиента. Archive убирает их из активного списка и сохраняет восстановление; это не вечное удаление. Диспетчер и чужие чаты остаются. Не редактируй внутренние базы клиента. Для Claude Code используй видимые чаты и cleanup только при фактической поддержке host; не заявляй отсутствующую интеграцию. CLI-native сессии сохраняются для resume, но их ID не означает видимость в приложении. Универсального desktop chat backend в CLI нет: описанный host workflow выполняет координатор через app tools.

1. Вызови `kodo doctor --json`. Используй текущий клиент `codex` или `claude-code`. В OpenCode возьми настроенный backend подписки; не выбирай сторонний API вместо него. По умолчанию оставь один клиент. Если пользователь явно пишет «используй обе подписки», добавь `--providers both`.
2. Подготовь запуск: `kodo run "<поручение пользователя>" --client <client> --project <корень проекта> --prepare --json`. Сохрани возвращённый `id` как runId. Прочитай `analysis`, `research` и материалы из каталога `artifacts`. Не копируй ключи или приватные конфигурации в план.
3. Прочитай `plan-context.md` в каталоге `artifacts`: Kodo уже выбрал применимые стандартные навыки и проверил закреплённые источники. Составь план именно текущей основной моделью чата. Запиши `plan.json` в каталог `artifacts` этого запуска вне репозитория. Корень плана: `summary` и `tasks`. Каждый узел содержит `id`, `role` (`developer`, `tester` или `documenter`), `description`, `dependsOn`, `writePaths`, `acceptance`, `parallel`. Идентификаторы уникальны; зависимости существуют и не образуют циклы. Области записи относительны проекту. Разделяй независимые части, но не назначай параллельную запись в общие файлы. Включи проверку изменённого поведения и затронутую документацию.
4. Передай план: `kodo resume <runId> --plan <абсолютный путь к plan.json>`. Следи за запуском через `status` и `logs` до конечного результата или конкретного технического блокера. Для продолжения используй этот runId; не создавай новый запуск из-за прерывания чата.

Проверь optional tools через `kodo tools list --json` и `kodo tools doctor --json`; `tools doctor --live` также проверяет только версии/import metadata, не вызывает UI/модель. Установку по точным pins и live UI/security gates выполняет координатор. У старых проектов оба gate выключены; у самого Kodo security включён, UI выключен как для CLI. Для включённого UI настрой cases с независимыми DOM/accessibility assertions, собственными профилями и endpoint; service credentials получают только нужные bridge. После build/test нужны актуальные `run.uiVerification`/`run.securityChecks`, затем независимое review; stale head/config/pins или испорченное evidence блокирует delivery. Disabled означает `passed:null`, а не успех. Playwright-шаблон и опциональный Chrome MCP не доказывают установку/подключение.

Узлы получают bounded task context с writePaths, acceptance, interfaces, constraints и краткими прямыми зависимостями; не вкладывай историю и прежние промпты. В артефактах запуска `progress.md` восстанавливается из SQLite и показывает переходы/проверки/блокеры. По умолчанию бюджет ремонта пять, явный меньший сохраняется; повтор без прогресса может остановиться раньше. Исчерпание сохраняет controller assessment и блокирует автоматические повторы. `resume --retry-failed` используй только как явное новое поручение после устранения причины: прежняя история остаётся.

Поручение включает необходимые действия выполнения и настроенной доставки: обычные commit, push, PR, merge, release, настроенные deploy и smoke уже разрешены, повторные вопросы не нужны. Выполняет их координатор, с актуальными checks и branch protections; workers не начинают собственную доставку. Соблюдай действующие ограничения клиента и проекта. Отсутствующий доступ, внешний запрет или неподтверждённое выполнение не заменяй обещанием успеха.

В конце сообщи фактический результат и доказательства: изменённое поведение, проверки, PR, merge commit, выпуск и проверку установленного/развёрнутого результата, если стадии состоялись. Если запуск ждёт лимита или заблокирован, назови состояние и причину. Не называй push деплоем и не объявляй непроведённую проверку успешной.
