# Этапы 15–16: движок большого проекта — параллельно, быстро, правильно

Статус на 2026-11-24: **в работе.** Решение — [ADR-0017](../decisions/0017-parallel-engine.md). План составлен с Gemini 4 Neon и сведён координатором. Пользователь утвердил выполнение всего плана до конца (2026-11-24). Воркеры: `codex/gpt-6.2-astra`, `antigravity/gemini-4-neon`, Claude Opus 5.5. Машина — только этот ПК, пока пользователь не назовёт другие.

## Видение пользователя

Kodo — движок, который позволяет ИИ не просто работать параллельно, а работать **быстро и правильно** над очень большой целью. Пример масштаба — большая воксельная игра на Rust. В начале каждой задачи пользователь сам называет подписки и машины.

## Этап 15 → выпуск 1.1.0

Интеграционная ветка `kodo/15-engine`. Каждый стрим — отдельная ветка и worktree, red/green тесты, только свои проверки (полный `npm run check` — у координатора), два независимых ревью разных провайдеров.

### 15A. Профиль запуска, снятие потолков, критический путь (`kodo/15a-scale`)

- `ExecutionProfile v1` в состоянии проекта (SQLite, вне Git): `subscriptions` — провайдер/модель, слоты, тир (`heavy`/`standard`/`fast`), `cooldownUntil`; `machines` — `id`, `kind` (`local`/`t3-env`/`ssh`), `maxWorkers`, `maxHeavyBuilds`.
- CLI: `kodo project profile set|show|pause-pool`. Без профиля — прежнее поведение.
- Потолки 5/24/8 заменяются пределами профиля с жёстким верхним ограничением безопасности (64 слота); значения по умолчанию прежние.
- Готовые задачи упорядочиваются по критическому пути (глубина потомков, затем число прямых потомков, затем стабильный ключ).
- Скользящее окно: `next-wave` выдаёт задачи на свободные слоты, не дожидаясь завершения волны; бриф несёт рекомендованную подписку и машину.
- Приёмка: тесты профиля и CLI, порядок критического пути, выдача > 5 задач при профиле, отказ сверх слотов, `cooldownUntil` исключает подписку.

### 15B. Асинхронная проверка и очередь интеграции (`kodo/15b-queue`)

- `complete-task` проверяет Git, область записи и секреты под короткой блокировкой, а `task-fast` — под семафором машины `machine-build:<id>` (`maxHeavyBuilds`), не держа `project:<id>`.
- `runtime/project-integration-queue.mjs`: очередь проверенных коммитов в SQLite с приоритетом критического пути, пакетный дренаж непересекающихся задач; конфликт — `project_integration_conflict` без порчи ветки проекта.
- Гейты независимых эпиков параллельно: блокировка на уровне эпика.
- Приёмка: две сдачи одновременно не ждут друг друга на `task-fast`; очередь сохраняет порядок и переживает перезапуск; нет `integration_busy` при 10 одновременных сдачах в тесте; гейты двух эпиков идут одновременно.

### 15C. Rust и Cargo workspace, быстрый цикл сборки (`kodo/15c-rust`)

- `quality.mjs`: виртуальный `[workspace]`, `edition.workspace = true`, `Cargo.lock` и `rust-toolchain.toml` в корне workspace.
- `runtime/cargo-graph.mjs`: затронутые крейты по диффу и их потребители; `task-fast` запускает `cargo check -p`/`cargo test -p`, при правке корневого `Cargo.toml`/`Cargo.lock` — весь workspace.
- Настраиваемый `fastChecks.timeoutMs` (Rust по умолчанию 600 с).
- Слоты `CARGO_TARGET_DIR` по машине (`maxHeavyBuilds`), необязательный `RUSTC_WRAPPER=sccache` при наличии; прогрев зависимостей после Волны 0; уборка worktree после `integrated`/`abandoned`.
- Приёмка: фикстура workspace из 3 крейтов проходит профиль; дифф в листовом крейте запускает только его и потребителей; правка корня — весь workspace; слоты не пересекаются.

### 15D. Контекст и обратная связь для агента (`kodo/15d-context`)

- `runtime/api-cards.mjs`: детерминированная карта публичного API зависимостей задачи (Rust `pub` элементы, JS/TS `export`) на `baseSha`, без вызовов модели, с пределом размера; обязательная часть брифа в `ContextManifest`.
- `runtime/diagnostic-pack.mjs`: сводка ошибок `cargo --message-format=json`, `node:test`, гейтов в `{ file, line, code, message, failingTests[] }` для брифа ремонта.
- Проверенные уроки гейтов (`verifiedLessons`) попадают в брифы следующих задач того же модуля.
- Линтер чертежа: слишком крупные задачи → `split_required`, у каждого модуля один владелец, общие файлы (`Cargo.toml`, точка входа) — отдельные задачи-интеграторы.
- Приёмка: снимок карты API на фикстуре Rust и JS, предел размера, пакет ошибок из реальных JSON-сообщений `rustc`, урок попадает в бриф, линтер отклоняет задачу без владельца.

### 15E. Правильность: контракты, архитектура Rust, честные тесты

Два стрима, чтобы не мешать друг другу:

- **15E1 (`kodo/15e-architecture`)** — Architecture Guardian для Cargo workspace (`cargo metadata --no-deps` или разбор `Cargo.toml`): слои и запрет обратных зависимостей и циклов, список разрешённых внешних крейтов, защита контрактного крейта от правок обычной задачей; правило чертежа «Волна 0 создаёт компилируемый контрактный крейт» для многомодульных проектов.
- **15E2 (`kodo/15e-behavior`)** — Behaviour Gate для Rust: комментарии и raw-строки, `#[cfg(test)]` внутри `src/**/*.rs`, сверка реестра тестов `cargo test -- --list` (база и голова), отказ `weak_or_empty_test` на пустое тело или `assert!(true)` в изменённом тесте; шаблоны оракулов (свойство, бюджет производительности, headless smoke).
- Приёмка: обратная зависимость, цикл, неразрешённый крейт и правка контракта отклоняются; закомментированный или пустой Rust-тест отклоняется; удаление теста в `src/` замечено.

### 15F. Координация Cargo.lock (`kodo/15f-cargo-lock`)

Появилась после сверки 15E1. Параллельная задача, которая меняет манифест своего крейта, может менять и корневой `Cargo.lock`. Разрешены только добавление и удаление пакетов. Для замены версии, источника или checksum нужен явный путь. Конфликт, затронувший только `Cargo.lock`, интеграция регенерирует офлайн во временном дереве; merge-коммит получает trailer `Kodo-Lock-Regenerated`. Подробности — в docs/RUNTIME.md.

### Известные ограничения 1.1.0

- Исправлено в 1.1.2. Гейт Rust учитывает происхождение слияний соседних эпиков при проверке изменений контрактного крейта.

- Квитанция Engine для гейта эпика сверяет задачи с `run.nodes`. Соответствие манифесту слияний проверяет Project Director (`validateWaveGate`) до принятия гейта.
- Полный гейт Rust собирает голову в проверяемом рабочем дереве. Нужны закоммиченный `Cargo.lock` и игнорируемый `target/`, иначе гейт останавливается с `dirty_worktree`. Сверку реестра отключает `verification.testRegistry: false`.
- Регенерация `Cargo.lock` выполняется офлайн. Cargo-конфиг проекта и `rust-toolchain.toml` действуют, как в task-fast. Песочницы нет, модель доверия описана в docs/SECURITY.md.

### Контрольная точка 1: пилот Voxa (2026-11-25) — ACCEPTED

Проект «Voxa» — оригинальная headless-песочница на Rust, только std. В ней 8 крейтов: контрактный `voxa-contracts` и world, gen, mesh, physics, io, sim, cli. Работа шла 17 задачами, 8 эпиками и 2 майлстоунами. Волна 0 заложила workspace, контракт, политику архитектуры и заготовки крейтов.

Профиль: Codex gpt-6.2-astra (4 слота, heavy) и Gemini 4 Neon (4 слота, standard). Машина одна — этот ПК, 8 воркеров и 1 тяжёлая сборка. Диспетчер — главный чат T3, воркеры — видимые чаты `delegate_task`. Задачи разделились так: Codex — 8, Gemini — 9.

Итог: `kodo report` — проект `accepted`, 17/17 задач, 8/8 эпиков, 2/2 майлстоуна, блокеров нет. Принятый SHA `ee0c272` доставлен в `main` пилота fast-forward. Проверка на месте: `cargo test --workspace --locked` — 98 тестов, 0 падений. Демо `voxa --seed 42 --radius 1 --ticks 40` детерминировано, сохранение и перечитывание совпадают.

Пилот нашёл два дефекта Kodo. Оба исправлены выпусками с независимым ревью:
- **1.1.1.** Общий `CARGO_TARGET_DIR` слота task-fast отдавал задаче артефакты worktree другой задачи. Это дало ложный `checks_failed` на `mesh-greedy`; так же возможен был и ложный PASS. Теперь слот при смене worktree начинается пустым, а `CARGO_BUILD_BUILD_DIR` указывает внутрь слота.
- **1.1.2.** Ремонт контрактного крейта гейтом Волны 0 вернулся в ветку после слияний других эпиков и блокировал их гейты (`contract_change_not_allowed`). Теперь гейт проверяет каждый коммит диапазона правами его источника.

Подтверждено вживую:
- неявное право на `Cargo.lock` (15F) сработало 4 раза: `sim-entity`, `mesh-perf`, `sim-light`, `cli-demo`. Регенерация не понадобилась — правки lock сливались без конфликта;
- гейты эпиков шли параллельно (physics и world).

В бэклог этапа 16:
- самопроверка `ci feedback` на Rust всегда `blocked`: нет пинов `rustc`/`clippy` (`exact_*_pin_required`), `affected_graph_fallback`, конфиг-файлы Волны 0 не сопоставляются. Нужен пин toolchain в правилах Волны 0 или мягкая деградация;
- Gemini иногда завершает ход до результата: хосту нужен автоматический повтор;
- `cargo-graph` нужно перевести на общий резолвер `cargo-workspace`.

## Этап 16 → выпуск 1.2.0

### 16A. Удалённые машины

Git-транспорт `refs/kodo/<projectId>/base|work/<runId>`, брифы без локальных путей для `t3-env`/`ssh`, проверка `task-fast` на удалённой машине с квитанцией, привязанной к `headSha` и хэшу политики; проверка доступности машин и переназначение задач отвалившейся машины.

16A — Git-транспорт удалённых попыток и квитанции task-fast. Живой прогон на реальной удалённой машине — NOT RUN.

### 16B. Автономность на сотнях задач

Арбитр гейта на другой подписке из профиля (`confirm_pass`/`confirm_defect`/`split_needed`); автоповтор `project_integration_conflict` от свежей головы с прошлым диффом (до 2 раз); живой сторож внешних воркеров (нет прогресса, повтор одной ошибки, выход за область записи → подсказка → `--abandon` и переназначение); пределы чертежа и `extend`/`append-milestone` для 50+ задач на веху.

- **16B1 (`kodo/16b1-arbiter`).** Арбитр гейта. Отказ ревью после исчерпанного ремонта при зелёных детерминированных проверках, включая smoke, рассматривает одна сессия на подписке другого провайдера из профиля. Сессия одна на gate Run. Решения: `confirm_pass` — гейт принят по `gateArbitration`, привязанному к head и квитанции ревью; `confirm_defect` — блок, как раньше; `split_needed` — `gate_split_needed` со `splitWork`. Без профиля или второй подписки поведение прежнее. Отчёт показывает число арбитражей. Подробности — [VERIFICATION.md](../VERIFICATION.md), «Арбитр гейта».

### 16C. Телеметрия и диспетчер T3

`kodo report --project`: задач в час, p50/p95 задачи, разбивка времени (агент, сборка, очередь, гейт, квота, человек), First-Pass Yield, арбитражи, вмешательства, загрузка подписок и машин. Навык `kodo-project-director` и [T3-HOST](../T3-HOST.md): старт с `profile set`, цикл скользящего окна, передача подписки и машины в `delegate_task`, архив чата сразу после интеграции.

### 16D. Бэклог живого пилота (`kodo/16d-pilot-backlog`)

Самопроверка `kodo ci feedback` на Rust-проектах: правило Волны 0 `rust_toolchain_required` для `rust-toolchain.toml` (`channel = "1.x.y"`, `clippy`, `rustfmt`), предупреждение `toolchain_unpinned` вместо `blocked` только в самопроверке воркера (гейты и `task-fast` без ослабления), выбор затронутых крейтов по графу Cargo без `affected_graph_fallback`, классификация конфиг-файлов Волны 0 (`.gitignore`, `architecture.policy.json`, `Cargo.lock`, `rust-toolchain.toml`). Перевод `cargoMembers` (`runtime/cargo-graph.mjs`) и `rustWorkspaceRoots` (`runtime/quality.mjs`) на канонический `resolveCargoWorkspace` (`runtime/cargo-workspace.mjs`) с консервативным `cargo-workspace-unsupported` при `unsupported` и дифференциальным тестом по фикстурам `cargo metadata`.

### 16E. Запас времени Windows CI (`kodo/16e-ci-headroom`)

19 самых долгих тестовых файлов вынесены в обязательный шаг CI `npm run test:heavy`. Волновые тесты получили 900 с вместо 300 с. Отдельный тест проверяет, что каждый файл запускается ровно в одном шаге. Полная локальная проверка теперь состоит из четырёх команд: `npm run check`, `npm run test:heavy`, `npm run test:waves` и `npm run test:final`.

### Известные ограничения 1.2.0

- **16A.** Удалённые машины проверены только эмуляцией: второй клон и bare-репозиторий. Живой прогон на реальной SSH- или T3-машине — NOT RUN, по решению пользователя только этот ПК. Квитанция `trustedBuilds` не подписана. Она означает доверие диспетчера машине и каналу передачи файла. Гейт эпика всегда проверяет локально.
- **16B1.** Лимит повторов арбитража можно сбросить только перезаписью сохранённого Run в SQLite Kodo — это вне модели угроз из docs/SECURITY.md. Решение `split_needed` только перечисляет работу, само `extend` не вызывает.
- **16B2.**
  - Если в истории симлинк заменён обычным файлом, дифф прошлой попытки может разойтись со статистикой.
  - Сбой `git diff` при захвате даёт ошибку вместо `truncated`.
  - Линтер на 400 задачах, у которых glob-пути лежат в одном общем каталоге, остаётся квадратичным.
- **16D.**
  - JS-проект с файлами `*.rs` в writePaths получает требование `rust-toolchain.toml`.
  - Rust только в подкаталоге без политики v2 не распознаётся линтером: task-fast остановит задачу позже.
  - Если корень чертежа — подкаталог репозитория, закоммиченный `rust-toolchain.toml` не находится.
- **Квитанции этапа 15** остаются в силе (см. «Известные ограничения 1.1.0»).

### Интеграция 1.2.0 и контрольная точка 2
