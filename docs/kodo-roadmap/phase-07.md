## Соответствие приёмке MVP

| Требование | Чем подтверждено |
| --- | --- |
| Dependent не стартует до интеграции prerequisite | Store: dependent не выдаётся при `verifying` и `integrating`. Git-цепочка: worktree задания `c` уже содержит файл `a` |
| Конфликтующие scopes сериализованы | Одинаковые и вложенные `writePaths` не пересекаются по времени; второе задание стартует после интеграции первого |
| Каждое изменение интегрируется не более одного раза | Один слот интеграции; повтор квитанции — no-op, другая квитанция — конфликт; после сбоя merge сверяется и не повторяется (Git: в `main` ровно один merge задания) |
| Lost lease, cancel, quota, restart не дублируют исполнение | Старый worker получает `job_lease_lost`, его результат отбрасывается; записанный результат после перезапуска не исполняется |
| Управляемое перекрытие подтверждено fixture | При 1/2/4/8 слотах наблюдаемое перекрытие равно лимиту, интеграция строго по одной |
| Нет неконтролируемых внешних вызовов | Модули jobs не обращаются к провайдерам и сети; исполнение и интеграция — только переданные порты |

Устойчивость тестов к ошибкам реализации проверена 11 ручными мутациями (зависимость по `verifying`, снятие слота интеграции, отключение резервирования и старения, доверие чужому токену, слепой повтор интеграции, отключение heartbeat, транзакция без `IMMEDIATE` и другие): каждую ловит хотя бы один тест.

## Независимое ревью

Первая версия прошла read-only ревью отдельным агентом, не видевшим хода разработки. Он нашёл 9 дефектов и 2 слабых теста. Все исправлены, на каждый добавлен тест, который падал до исправления:

| Замечание | Исправление |
| --- | --- |
| `kodo jobs` создавал базу, выполнял миграцию и брал блокировку записи | `openJobReader`: read-only, без миграции; на пустом home ничего не создаётся |
| Отклонённый хранилищем результат останавливал очередь | Задание сразу `failed: result_rejected:<код>`, очередь продолжает; негодный checkpoint не срывает паузу по квоте |
| После зависания планировщик мог повторно запустить своё живое задание | Свои аренды продлеваются перед каждым sweep; учёт по токену аренды |
| Интеграция, завершённая после перехвата аренды, проглатывалась | Явная ошибка `job_integration_ownership_lost`; порту дан `confirmOwnership()` |
| Голодающее задание, которое не может стартовать, блокировало чужую работу | Резерв только у задания, способного стартовать; резерв учитывает locks |
| `beginIntegration` блокировал задания подключённого host | Sweep без сведений о host не принимает решений о host |
| После паузы по квоте задание теряло locks | Задание остаётся `waiting_quota` до возобновления и удерживает scopes и locks |
| Пустая очередь давала `integrated` | Статус `empty` |
| CLI выдумывал `host_unavailable`/`worker_mismatch` | `waitingFor` показывает только причины, видимые из очереди |
| Тест «только чтение» не ловил создание таблиц; тест двух соединений был тавтологией | Тесты на свежий home, legacy-базу и открытую транзакцию записи; тест с четырьмя процессами |

Остаточный риск из ревью: окно двойной интеграции при зависании координатора дольше TTL аренды нельзя закрыть без fencing на стороне Git. Оно описано в [JOBS](../JOBS.md) и [ADR-0009](../decisions/0009-durable-jobs.md).

## Подключение Engine

Подключение сделано на уровне Engine, а не Project Director. Причина: настоящая параллельность в Kodo сегодня существует между узлами плана внутри Run, с отдельными worktree и merge координатором. Director ведёт одну Attempt за вызов, и каждая Attempt — это Run.

Путь включается явно ключом `"scheduler": "durable"`; без него работает прежний `runReadyQueue`, и ни один существующий тест не меняет поведение. Правила прежнего диспетчера сохранены: лимит `concurrency`, запрет параллельности из плана и от Jev, остановка стартов после первого сбоя, бюджет ремонтов, пауза по квоте, отмена и `--retry-failed`. Проверено тестами: порядок зависимостей, перекрытие двух независимых узлов, сериализация общего файла, квота с соблюдением `retryAt`, исчерпанный бюджет, остановка с продолжением в новом процессе и сбой сразу после merge без повторного merge.

Устойчивость тестов подключения проверена 4 мутациями: без паузы стартов, без `takeOver` и без запрета параллельности тесты падают. Четвёртая (повтор остановленного узла при обычном `resume`) эквивалентна по поведению: Engine сам отказывает остановленному узлу без сессии.

## Что не сделано

- **Включение по умолчанию.** `durable` остаётся opt-in до нативного пилота; решение записано в [ADR-0009](../decisions/0009-durable-jobs.md).
- **Параллельные Attempt в Project Director.** Для них нужен merge расходящихся head разных Run; сложный batch merge отложен по [NEXT-STAGES](NEXT-STAGES.md).
- **Анализ Gemini и оценка Jev** перед этапом не выполнялись: в этой среде нет настроенного Kodo runtime с провайдерами. Контракты заморожены по [NEXT-STAGES](NEXT-STAGES.md) и исходному сценарию 07.
- **Реальный нативный пилот** подписочных клиентов не запускался. Все свидетельства этапа — offline: fake providers, настоящие Git и SQLite.
- **Adaptive concurrency** по CPU/RAM/диску/CI отложена по [MVP-SCOPE](MVP-SCOPE.md).

## Ограничения

- Fixture с временем (`8 × 40 мс`, 1 слот против 4) показывает сокращение wall time только на управляемой нагрузке. Об ускорении реальных задач она ничего не говорит.
- Лимиты задаются явно: 1–8 workers у очереди, 1–5 у Engine (`concurrency`).
- Хранилище не может запретить внешний merge. Единственность координатора проекта обеспечивает аренда `project:<id>` из этапа06.
- Адаптеров `t3`/`orca` нет: такие задания получают `blocked: host_unavailable:<id>`.
