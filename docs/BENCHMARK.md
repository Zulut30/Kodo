# Парный benchmark Kodo и native-клиента

Benchmark сравнивает обычный запуск подписочного клиента (`plain`) с реальным `Engine.create/run` Kodo (`kodo`) на одинаковых небольших задачах и фиксированной модели. Он измеряет правильность, соблюдение области изменений и затраты времени/наблюдаемых действий. Быстрый правильный результат — отдельная цель: одна лишь правильность не доказывает эффективность Kodo.

На 3 ноября 2026 года измеренный 24-trial пилот ещё не запускался. Этот документ задаёт методику и команды; победитель, ускорение, native latency, опубликованный пакет и deployment не заявлены. Офлайн-тесты с подменёнными провайдерами проверяют runner, но не дают реальных результатов моделей. Команды относятся к текущим исходникам; наличие benchmark в историческом Release 0.2.1 не подтверждается.

## Запуск, продолжение и отчёт

Нужны Node.js 24, Git и авторизованный официальный Codex или Claude Code с доступной подписочной моделью. GPT/Claude API fallback отсутствует. Kodo вызывает раннюю оценку Jev даже при явном режиме; если его ключ недоступен, записывает fallback, сохраняя явный режим. Ключи остаются у координатора. Для standard/deep анализ Gemini требует его настройки; настройки исследования fixture описаны ниже.

```powershell
node cli/index.mjs benchmark run --client codex --models gpt-6.1-sol,gpt-6-astra,gpt-6.1-terra --mode quick --repeats 2 --seed 1 --output "D:\KodoBenchmarks\quick-pilot" --json
node cli/index.mjs benchmark resume "D:\KodoBenchmarks\quick-pilot" --json
node cli/index.mjs benchmark report "D:\KodoBenchmarks\quick-pilot" --json
```

Для установленного CLI с этой возможностью замени `node cli/index.mjs` на `kodo`. `run` и `resume` выполняют реальные подписочные сессии и расходуют квоту. `report` только читает сохранённую квитанцию, не вызывает модель и не запускает испытания заново.

| Параметр `run` | Контракт |
| --- | --- |
| `--models` | Обязательный список 1–32 уникальных native model ID через запятую, без пробелов вокруг ID; capability probe проверяет фактическую доступность |
| `--client` | `codex` или `claude-code`; без флага используется `codex`, поэтому передавай текущий клиент явно; обе подписки автоматически не запускаются |
| `--mode` | `quick`, `standard`, `deep`; по умолчанию `quick` |
| `--repeats` | Целое 1–100, по умолчанию 2 повторения каждой пары |
| `--seed` | Знаковое 32-битное целое, по умолчанию 1; задаёт воспроизводимое перемешивание очереди |
| `--output` | Абсолютный путь каталога; без него создаётся отдельный временный каталог, его путь возвращается в `output` |
| `--json` | Структурированный отчёт вместо краткого текста |

`resume` и `report` принимают один PATH — каталог результата или его `benchmark.json` — и необязательный `--json`. Другие настройки при продолжении не передаются. Для Claude Code запускай отдельное сравнение, например с `--client claude-code --models sonnet,opus`, и отдельным output. Не смешивай его результаты с Codex без указания различий клиента и token semantics.

## Матрица и равные условия

Начальная матрица: две fixture × три доступные модели Codex × два условия × два повтора = **24 запланированных trial, 12 пар**. Это размер плана, не число состоявшихся успешных испытаний. Недоступная/неподтверждённая модель попадает в `excludedModels`, а её trial не планируются. Capability probes выполняются отдельно от trial и имеют собственные `probeMetrics`; auth/quota/unavailable при probe приостанавливают запуск до явного resume.

| Fixture | Задача | Независимая проверка |
| --- | --- | --- |
| `button-color` | Изменить обычный background `.button` в `src/button.css` на `#7c3aed` | Точные декларации и сохранность hover/focus-visible/disabled и остальных свойств |
| `filename-extension` | Исправить `src/extension.cjs`: lowercase extension последнего компонента пути | Точки в каталогах, оба разделителя, uppercase, hidden names, отсутствие расширения и trailing dot |

В каждой паре одинаковы исходный commit, task prompt, файлы, разрешённые native tools и выбранная модель. У каждой ячейки свои repo/worktree, сессии, SQLite-состояние, уроки и локальные кэши. Native memory generation/use отключены на каждый вызов в обоих условиях; файлы подписочной авторизации не копируются. `--last` и история другой ячейки не используются. Условия выполняются последовательно в seeded-порядке; baseline и Engine используют общие account-level subscription leases, не отдельный обход лимита через trial Store. Общий предельный лимит подписочных сессий — 2; benchmark выполняется последовательно.

Plain получает задачу напрямую в свежую native-сессию. Kodo запускает тот же production Engine со штатными worktree, планированием, проверками и отдельным свежим независимым review; это не имитация «Kodo shortcut». Во всех его native-сессиях модель фиксирована, включая planner/reviewer/повторы. Несовпадение сообщённой модели фиксируется как неуспех, а не скрытая замена.

Fixture config одинаков в обоих условиях: `primaryModel` и model allowlist фиксированы, `concurrency:1`, `repairRounds:1`, `researchBudget:0`, тест — `node verify.cjs`, build/deploy/smoke пусты, delivery выключена, UI/security по умолчанию disabled. Исходники вспомогательных файлов, config и теста должны сохраниться. Benchmark не делает PR/push/release/deploy fixture. `--mode standard`/`deep` по-прежнему сохраняет меньшие бюджеты fixture: это сравнение соответствующего режима с этими ограничениями, а не измерение полного профиля с research 10/40 или многими ремонтами.

Kodo добавляет 13 закреплённых default skills, оркестрацию и независимое ревью к тому же prompt. Это намеренное различие условий, которое нужно раскрывать при сравнении. Аккаунт, установленный клиент, машина, сеть и backend cache остаются общими; backend cache принудительно сбросить нельзя. Это парная методика на малой выборке, не идеальная изоляция внешней нагрузки.

## Правильность и защита от подмены проверки

Общий доступный `verify.cjs` — только smoke. После завершения модели координатор выполняет held-out oracle вне её рабочего дерева; код oracle не передаётся в prompt и не записывается в subject repo. Проверяются отдельно `correctness` и `scope`: tracked, untracked и ignored additions, вспомогательные исходники, конфигурация и test harness сравниваются с исходным snapshot. Изменять разрешено только implementation-файл fixture. Правильный ответ с лишними изменениями не проходит scope.

`passed` требует одновременно успешного исполнения, правильности по oracle и соблюдения scope. Ответ модели `complete:true`, exit 0 smoke или собственное заверение модели не являются verdict правильности. Ошибка испытуемой модели остаётся завершённым неуспешным trial, а не падением всего benchmark. Наличие всех завершённых ячеек (`complete:true`) и exit code 0 CLI означают сформированный отчёт, а не 100% правильных решений.

## Квитанции и восстановление

`benchmark.json` записывается атомарно и сохраняет идентичность методики `paired-native-engine-heldout-v1`, опции, model IDs, версию клиента, commit/версию и SHA-256 исходников Engine, fixture hashes, trial IDs и pair keys. `resume` сверяет идентичность с текущими исходниками и клиентом. Изменение runner/fixture/опций/версии не объединяется со старой серией; нужен новый запуск. В установленном пакете Git commit может быть неизвестен, поэтому сохраняются также source hashes.

Quota, auth, отмена, недоступность или потеря lease оставляют текущую ячейку pending. После устранения причины запускай `benchmark resume PATH` явно. Завершённые ячейки не дублируются. Прерванная Kodo-ячейка продолжает только своё Engine-состояние; plain-повтор получает новую сессию и repo. Время ожидания между командами resume в измерение trial не входит. После аварийного завершения без финальной квитанции попытки неполное время остаётся неизвестным, а не восстанавливается догадкой.

Engine сохраняет выбранный режим и бюджет; автоматического escalation нет. Успешные локальные checks допустимо переиспользовать только по точному чистому HEAD, test/build-командам и Node/ABI/platform/arch fingerprint, с полным списком exit 0. UI/security и независимое review наблюдаются свежими. [Подробный контракт восстановления](RUNTIME.md#повторное-использование-локальных-checks).

## Как читать измерения

| Поле отчёта | Что наблюдается и где граница |
| --- | --- |
| `trials[].wallMs` | Полное активное время попыток ячейки: setup, очереди/leases, оркестрация, native-выполнение, проверки и oracle; без паузы между resume и отдельных probes; при утраченной длительности — `null` |
| `metrics.sessions`, `metrics.durationMs` | Число попыток native-сессий и сумма их наблюдаемой длительности, включая планирование/реализацию/ревью/повторы; это не чистое время генерации модели |
| `metrics.toolSteps` | Реальные завершённые native tool/command events без дубликатов start/update; недоступный stream даёт `null` |
| `metrics.coordinatorLogicalCalls` | Для Kodo отдельно assessment/analysis/research/routing/discovery; авторитетные Engine-счётчики не удваиваются обёрткой runner |
| `metrics.researchRequests` | Новые внешние запросы исследования, без cache reuse; это не сумма всех API-запросов |
| `metrics.usage`, `completeness` | Нормализованные nullable token-поля и доля доступных измерений; неизвестное не считается нулём |
| `metrics.nativeRequestCount` | Всегда `null`: реальный backend HTTP-счётчик native-клиента не наблюдается |
| `reportedModels`, `engine`, `clientVersion` | Запрошенная/сообщённая модель и доступные версии/hashes; действительная backend-реализация модели независимо не проверяется |

Codex `inputTokens` включает `cachedInputTokens`: total = input + output без повторного сложения cache. Claude `cacheReadTokens`/`cacheWriteTokens` отдельны от input, total считается только при известных input + cache read + cache write + output. Для desktop host usage может отсутствовать. Неполные агрегаты остаются `null` с `completeness`; попытки с ошибками не исчезают. По этим значениям нельзя вычислить точную цену подписки или точное число запросов.

`summaries` показывает `total`, `completed`, `passed`, `failed`, `pending`; `passRate = passed/completed`, pending не превращаются в failed и видны отдельно. `medianWallMs` учитывает все завершённые ячейки с известным временем, включая неуспешные, а `knownWallCount` раскрывает объём измерений. `medianPassingWallMs` относится только к прошедшим ячейкам; её следует читать вместе с числом failures и размером выборки.

`pairedDeltas` содержит Kodo минус plain для полного времени, tool steps и total tokens, только когда обе ячейки пары завершены и соответствующие измерения известны. Положительная временная дельта означает больше времени Kodo. Пары с неуспехом не скрываются: рядом есть `plainPassed`/`kodoPassed`. Для незавершённой пары или неизвестного поля дельта — `null`.

Для вывода о скорости сопоставляй wall time, native-session duration и правильность в одинаковых парах. Разность wall/native duration включает setup, oracle, очереди и прочую работу; её нельзя называть исключительно стоимостью Kodo или чистой LLM latency. Две маленькие fixture и два повтора не устанавливают универсально лучшую модель или качество на больших проектах. До реального пилота числовой результат не заполняется; после него координатор добавляет проверенный обезличенный отчёт с failure/pending/excluded и условиями окружения. Сырые prompts, provider output, ключи и приватные traces в публичный отчёт не копируются.

Проверки методики и разделение уровней доказательств — в [VALIDATION](VALIDATION.md#режимы-метрики-и-парный-benchmark), архитектурное решение — [ADR-0003](decisions/0003-execution-modes-and-benchmarks.md).
