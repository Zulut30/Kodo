# Доставка без повторных внешних действий

Этап 11 начался с аудита существующей доставки. Почти всё требуемое уже было; добавлено только недостающее. Решения описаны в [ADR-0013](decisions/0013-delivery-operation-journal.md).

## Что уже было

| Требование | Где реализовано |
| --- | --- |
| Не создавать второй PR | Перед `gh pr create` ветка ищется через `gh pr list`; больше одного совпадения — `ambiguous_pr` |
| Не сливать дважды | `gh pr merge --match-head-commit`; после любой ошибки команды состояние PR читается заново; `reconcileDelivery` в начале каждой доставки |
| Не публиковать дважды | Проверка тега и commit, метка владельца в черновике (`kodo-release:<run>:<sha>`), загрузка только отсутствующих файлов без замены |
| Точное соответствие commit, тега, пакета и контрольной суммы | `npm pack` из отдельного worktree на commit слияния, `SHA256SUMS`, сверка скачанных байтов |
| Проверка установленного пакета | Установка именно этого `.tgz`, сверка имени, версии и `bin` с манифестом commit, затем `--help`, `list --json`, `validate --json` |
| Более старый результат не заменяет новый | `assertFreshRelease`, `assertCandidateFresh` перед публикацией |
| Очереди | Аренды `merge:<repo>:<base>`, `release:<repo>:<base>`, `release-version:<repo>:<base>` с heartbeat |
| Защита веток | Обязательные проверки и `kodo/review` читаются из настроек защиты; `--admin` не используется |
| Миграции | Project Store отклоняет неизвестную версию схемы и делает backup перед миграцией; job store отклоняет неизвестную версию |

Тесты этих свойств существовали до этапа: `tests/delivery.test.mjs`, `tests/release-finalization.test.mjs`, `tests/engine-2.test.mjs`.

## Что добавлено

### Журнал операций

Перед каждым необратимым внешним действием (создание PR, слияние, публикация выпуска) в события запуска записывается намерение, а после чтения удалённого состояния — исход:

| Исход | Смысл |
| --- | --- |
| `confirmed` | Этот вызов сам выполнил действие, и оно видно. Для PR — по URL, который вернула команда создания; для слияния и выпуска — чтением удалённого состояния |
| `reconciled` | Действие установлено только чтением удалённого состояния: команда этого вызова упала уже после того, как удалённая сторона её приняла, или действие выполнил прежний процесс |
| `absent` | Команда завершилась с ошибкой, и чтение сразу после неё показало, что действие не произошло. Пишется только для слияния. Обычно это отказ удалённой стороны; сетевой сбой внутри клиента выглядит так же, поэтому следующая доставка всё равно начинает с чтения PR |
| `uncertain` | Намерение есть, исхода нет: действие могло произойти, а могло нет |

`uncertain` — это не состояние ошибки, а указание следующему запуску: сначала прочитать удалённое состояние, повторять нельзя. Доставка так и делает; журнал делает это видимым.

Журнал осторожен в одну сторону: он скорее оставит `uncertain`, чем напишет `absent`. Команда слияния, которая вернулась, пока PR ещё открыт (очередь слияния, задержка GitHub), и команда, остановленная локальным таймаутом после отправки запроса, слияние не опровергают и остаются `uncertain`. Так же остаётся `uncertain` операция, после намерения которой запуск остановился по другой причине (ожидание проверок, устаревшее ревью, закрытый PR, отказ до публикации выпуска). Гипотеза о неподтверждённой операции добавляется в текущий блокер, когда он записывается впервые, и может относиться к прошлой попытке. Повторная остановка по той же причине на том же commit гипотезы не пересчитывает; гипотеза уходит вместе с блокером, когда он сменяется или снимается. Актуальное состояние операций всегда показывает строка `Delivery operations`.

Последующее чтение не переписывает историю: действие, которое запуск сам подтвердил, остаётся `confirmed`, а не становится `reconciled`.

Запись намерения обязательна: если её не удалось сохранить, внешнее действие не начинается. Запись исхода — наблюдение: её сбой не превращает уже состоявшуюся доставку с сохранённой квитанцией в ошибку, операция просто остаётся `uncertain`.

События имеют тип `delivery.operation` и содержат только идентификаторы: номер PR, тег, commit, SHA-256. Журнал добавляется к событиям и не меняет сохранённые квитанции.

```js
import { deliveryOperations, uncertainOperations } from './runtime/delivery-operations.mjs';

deliveryOperations(store.events(runId));
// [{ operation: 'pr', status: 'confirmed', attempts: 1, … },
//  { operation: 'merge', status: 'reconciled', attempts: 1, … }]
uncertainOperations(store.events(runId)); // ['release']
```

Engine сохраняет сводку журнала в `run.deliveryOperations`, когда запуск с включённой доставкой завершается или останавливается. Её видно в `kodo status` и в `progress.md`:

```
Delivery operations: pr confirmed; merge uncertain (read back before retry)
```

Если запуск остановлен с неподтверждённой операцией, новый блокер получает соответствующую гипотезу ([WATCHDOG](WATCHDOG.md)).

### Проверка установленного пакета привязана к артефакту

Квитанция проверки теперь называет байты, которые она устанавливала:

```json
{ "passed": true, "commands": ["kodo --help", "kodo list --json", "kodo validate --json"], "node": "v24.…", "platform": "win32", "artifactSha256": "…" }
```

Перед публикацией и при восстановлении опубликованного выпуска `artifactSha256` обязан совпадать с `sha256` выпуска, иначе `release_conflict`. `kodo audit` показывает это поле. Квитанции, сохранённые до этапа 11, поля не содержат и остаются читаемыми.

### Развёртывание не имитируется

В этой версии нет адаптера развёртывания. Для запуска с включённой доставкой в `run.deployment` записывается:

| Конфигурация | Статус |
| --- | --- |
| `commands.deploy` пуст | `not_configured` |
| `commands.deploy` задан | `not_run`, причина `no_deployment_adapter` |

`passed` в обоих случаях `null`. Развёртывание никогда не отмечается как пройденное.

## Восстановление вручную

1. `kodo status RUN_ID` — посмотреть `deliveryOperations`, `delivery` и `blocker`.
2. Если операция `uncertain`, ничего не повторять вручную. `kodo resume RUN_ID` сам читает удалённое состояние и либо записывает квитанцию, либо продолжает с этого шага.
3. Если операция `absent`, команда слияния упала и PR не слит; `resume` выполнит слияние заново обычным порядком, с теми же проверками актуальности базы и версии.
4. `stale_base` означает, что целевая ветка ушла вперёд: Engine синхронизирует базу, повторяет проверки и ревью и только потом сливает. Обойти это нельзя.

```powershell
node scripts/run-tests.mjs tests/delivery-operations.test.mjs tests/delivery.test.mjs
```
