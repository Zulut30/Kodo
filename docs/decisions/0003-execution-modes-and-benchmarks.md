# ADR-0003: Ограниченные режимы исполнения и парное измерение

**Дата:** 2026-11-03. **Статус:** решение задано контрактом run `aa3357f3-b19d-4a62-a54f-e11258c9fe05` и отражено в рабочих исходниках. Целевые локальные проверки указаны в [VALIDATION](../archive/VALIDATION.md#режимы-метрики-и-парный-benchmark); общий check/CI, реальный 24-trial пилот, выпуск и deployment требуют отдельных свидетельств координатора.

## Контекст

Безусловные Gemini-анализ, исследование, маршрутизация и отдельные роли добавляют задержку небольшой локальной правке. Пользователю важна скорость при сохранении настоящих проверок и независимого ревью. Подписочные клиенты не раскрывают чистую LLM inference latency, точный backend HTTP-счётчик и стоимость отдельной задачи в USD. Сравнение только успешных решений скрывает неуспех, а модельное заверение о правильности не заменяет независимый oracle.

## Решение

1. Сохранить существующие Node.js 24 ESM, SQLite, process/state/delivery границы, изолированные worktree, девять optional tools и все 13 закреплённых default skills. GPT/Claude исполнять только через авторизованные подписочные клиенты. Диспетчер и поддерживаемый host workflow остаются у координатора; workers не создают агентов/чаты и не получают provider keys.
2. До дорогого анализа оценить complexity/risk/scope одним typed Jev batch с confidence/probabilities. Quick автоматически допустим только для уверенных low/low/local без усечения релевантного контекста. High complexity/risk или cross-cutting даёт deep, прочее — standard. Недоступная/невалидная оценка записывается как fallback standard; отмена не поглощается. Явный `--mode` выше project mode и оценки.
3. Ограничить quick/standard/deep профилями research 0/10/40, maxTasks 2/12/24, repairRounds 1/3/5, concurrency 1/2/2. Применять меньшие настройки проекта. Quick получает local analysis без Gemini/research, одно рекомендуемое developer-задание с tests/docs и одну выбранную модель без отдельных routing-вызовов. `--model` фиксирует модель на всех native-этапах любого режима. Свежее независимое review, настроенные test/build и включённые UI/security остаются обязательными.
4. Фиксировать режим/бюджеты в run. Resume не меняет их и не повторяет завершённые стадии; явный retry открывает новый цикл в тех же пределах. Автоматическое повышение режима не реализовано. Более широкий budget требует нового run. Для старого сохранённого анализа использовать compatibility standard с прежними ограничениями и неполной историей метрик.
5. Для восстановления переиспользовать только полную успешную локальную check-квитанцию текущего чистого HEAD с точными командами и Node version/ABI/platform/arch fingerprint. Изменение этих условий требует нового прогона. UI/security и review всегда получают свежие наблюдения. Исчерпание/отсутствие прогресса сохраняет controller assessment и блокирует безграничные повторы.
6. Записывать наблюдаемые длительности, попытки, завершённые tool events, нормализованный nullable usage и отдельные логические операции координатора. Не складывать Codex cached input дважды, не терять Claude separate cache read/write. Неизвестное и неполное сохранять `null` с полнотой; HTTP counts и subscription USD не оценивать.
7. Сравнивать plain и production Engine парно на одинаковом исходном commit/prompt/model/tool permissions, со свежими repo/session/state/cache и account-level leases. Native memory отключать в обеих ветвях. Held-out oracle выполнять вне subject workspace, отдельно проверять scope и неизменность вспомогательных файлов. Фиксировать различие treatment: Kodo добавляет default skills, оркестрацию, checks и review.
8. Сохранять атомарные trial receipts и идентичность методики/версий/hashes. Quota/abort оставляют pending для явного resume без дубликатов завершённых ячеек. Отчёт показывает raw trial records, failure/pending/excluded, медианы с известным знаменателем и paired deltas. Пилот планируется отдельно: 2 fixture × 3 Codex-модели × 2 условия × 2 повтора, без утверждения результата заранее.

## Рассмотренные альтернативы

| Вариант | Причина отказа |
| --- | --- |
| Полный дорогой маршрут для каждой задачи | Добавляет вызовы и роли даже одной локальной правке |
| Быстрый маршрут без проверок и review | Не подтверждает качество изменённого поведения |
| Классификация по ключевым словам или безусловный strongest model | Не учитывает отрицания, уверенность и явный выбор пользователя |
| Скрытое повышение режима или неограниченный retry | Меняет согласованный объём работы и мешает прогнозировать задержку |
| Повтор всех шагов после quota | Теряет подтверждённые checkpoints; допустим только обоснованный повтор при изменении head/config/окружения |
| Старый UI PASS после нового провала | Не доказывает текущее наблюдаемое поведение |
| Имитация Engine, общий repo/cache или видимый модели oracle | Искажает сравнение и допускает подмену критериев |
| Только медиана успешных trial или USD по токенам | Скрывает неуспех и приписывает подписке ненаблюдаемую цену |

## Последствия и проверка

Quick ограничивает оркестрацию, но не гарантирует точное число native HTTP-вызовов или время ответа сервиса. Слишком узкий явный режим может блокироваться на проверках; он не повышается автоматически. Кэш checks снижает повторную локальную работу лишь при точной идентичности условий. Свежие gates и review сохраняют необходимую стоимость проверки.

Benchmark показывает наблюдаемый результат небольших fixture, а не универсального победителя. Wall time включает setup/проверки/oracle/очереди, native duration включает работу клиента и его инструментов; разность не является чистой стоимостью Kodo. Общие аккаунт, установка, сеть и backend cache ограничивают воспроизводимость. Fixture бюджеты research 0/repair 1/concurrency 1 сохраняются даже при выборе standard/deep.

Проверенный урок для следующих измерений: схема метрик и границы treatment должны быть зафиксированы до сбора чисел. Иначе двойной счёт assessment, смешение cached-token semantics или исключение failures создают ложный вывод о скорости/цене. Контракт проверяют независимые сценарии в `modes`, `mode-engine`, `metrics`, `benchmark` и `benchmark-cli`; точные имена и локальные ограничения приведены в VALIDATION. Офлайн GREEN не подменяет native pilot, проверенный release или deployment.
