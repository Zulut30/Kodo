# ADR-0009: durable jobs рядом с Project Director и legacy Run

Статус: решение для MVP07. Контракты, хранилище, планировщик, read-only CLI и opt-in подключение Engine реализованы. Приёмка07 этим ADR не утверждается: её фиксирует [отчёт этапа](../kodo-roadmap/phase-07.md).

## Контекст

Project Director (06) исполняет один активный Attempt за вызов. Engine внутри одного Run уже умеет параллелить узлы плана через `runReadyQueue`, но его состояние живёт в теле Run и не переживает границу процесса как очередь. Этапу07 нужны долговечные задания между задачами проекта: зависимость стартует только после интеграции предшественника, конфликтующие scopes идут по очереди, а сбой процесса, потеря аренды, квота и отмена не приводят к повторному исполнению или повторной интеграции.

## Решение и альтернативы

| Выбор | Альтернатива и причина отказа | Последствие |
| --- | --- | --- |
| Задания в additive namespaced таблицах `kodo_jobs`, `kodo_job_events`, `kodo_job_migrations` существующего Store | Отдельная БД дала бы вторую атомарную границу с Project Store и legacy leases | Одна SQLite-транзакция на решение; legacy `runs`/`events`/`leases` не меняются |
| Все решения о допуске внутри `BEGIN IMMEDIATE` (`claim`, `beginIntegration`) | Решение в памяти процесса, как в `runReadyQueue`, не защищает от второго процесса | Два соединения не могут запустить или интегрировать одно задание дважды |
| Чистый `admission()` в `job-contracts.mjs`, хранилище только применяет его | Правила внутри SQL трудно проверять и объяснять в статусе | Те же правила печатает `kodo jobs` как причину ожидания, без записи |
| Отдельное состояние `verifying`: результат записан, интеграции ещё нет | Считать завершённое задание готовым для зависимых: dependent стартовал бы со старого дерева | Dependent ждёт именно `integrated`; записанный результат больше не исполняется |
| Один слот интеграции на очередь; прерванная интеграция возвращается первой с `recovery: true` | Повторить merge после таймаута: возможен двойной merge | Вызывающий обязан сверить (`reconcile`), попал ли merge, до любой другой интеграции |
| Интеграцию повторяем только при подтверждённом отсутствии (`integrated: false`) | Повторять при любой ошибке: неизвестный исход превращается в дубль | Неизвестный исход останавливает очередь на этом задании с сохранением владения |
| Старение (`bypassed`) и резервирование scopes после 8 проигранных claim | Только приоритет: широкая или низкоприоритетная задача голодает | Свежая срочная работа не вытесняет готовое задание бесконечно |
| Квота — пауза `waiting_quota` с checkpoint, без расхода попытки, не более 12 раз | Считать квоту сбоем: исчерпание retry policy чужой причиной | Scope удерживается, слот worker освобождается, возврат идёт с приоритетом |
| `host` — поле задания отдельно от `pool`/`model`; известны `native`, `t3`, `orca` | Молча исполнять нативно, если адаптер не подключён | Неподключённый host даёт `blocked: host_unavailable:<id>` до подключения |
| Отдельный цикл `runJobQueue` над хранилищем | Обернуть `runReadyQueue`: он останавливает всю очередь при первой ошибке, не знает квот, приоритетов и чужих процессов | `runReadyQueue` остаётся диспетчером узлов внутри Run; новый цикл не дублирует его роль |
| Engine подключён по явному ключу `scheduler: "durable"`, по умолчанию прежний диспетчер | Заменить `runReadyQueue` сразу: более тысячи тестов и сохранённые Run опираются на его порядок, а нативного пилота очереди ещё не было | Существующее поведение не меняется; включение по умолчанию — отдельное решение после пилота |
| Задание узла имеет одну попытку; ремонты считает Engine (`repairRounds`) | Две политики повторов: расходились бы бюджеты и причины остановки | Один бюджет; задание `failed` означает «узел остановлен Engine» |
| `takeOver(queue)` под эксклюзивной арендой Run снимает аренды прежнего процесса сразу | Ждать TTL: `resume` после сбоя возвращал бы `busy` до минуты | Вызывать только под внешней арендой всей очереди; без неё аренды снимает только TTL |
| Состояние узла в Run — источник истины, задание идёт следом | Два равноправных журнала: расхождение после сбоя между записями | Повторный вход доводит задание до состояния узла no-op шагами, без сессии и merge |
| Шлюз моста удерживается от начала попытки узла до интеграции его результата | Удерживать только на время сессии: следующий узел стартовал бы от базы без результата непараллельного узла | Смысл `busy` прежнего диспетчера сохранён; после первого сбоя шлюз будит ожидающих, и они возвращают задания |

## Границы

- Worker только исполняет и возвращает результат. Он не интегрирует, не пушит и не запускает агентов; интеграция принадлежит координатору.
- Роль (`architect`, `developer`, `tester`, …) — метка задания. Сама по себе она не запускает модельную сессию; число ролей не равно числу одновременных моделей.
- Лимиты: 1–8 workers на очередь и 0–8 на подписочный pool. Обход лимитов провайдера не предусмотрен.
- Хранилище не может физически запретить внешний merge. Если координатор завис дольше TTL аренды интеграции, второй координатор по `reconcile` может не увидеть ещё не дошедший merge и интегрировать сам. `confirmOwnership()` перед необратимым шагом сужает это окно, а интеграция, завершённая после перехвата, даёт явную ошибку `job_integration_ownership_lost`. Единственность координатора проекта по-прежнему обеспечивает аренда `project:<id>` из06.
- Задание на паузе по квоте остаётся `waiting_quota` до фактического возобновления и всё это время удерживает scopes и locks: прогресс в его worktree не должен устареть.
- Резерв голодающего задания действует, только если оно само может стартовать. Иначе закрытый pool или неподключённый host останавливали бы чужую работу бессрочно.
- `kodo jobs` открывает базу read-only без миграции и блокировки записи. Причины ожидания, зависящие от координатора (host, capabilities, лимиты), отчёт не показывает.
- Миграция только добавляет таблицы, поэтому выполняется без backup. Неизвестная версия схемы отклоняется (`job_migration_unsupported`).

## Что отложено

Adaptive concurrency по CPU/RAM/CI, daemon, распределённый fleet, настоящие адаптеры T3/Orca и нативный пилот по ограниченному бюджету.
