# ADR-0015: pull-хост для видимых воркер-чатов T3 Code

Статус: решение этапов F2–F3. Приёмку этапа фиксирует [отчёт](../kodo-roadmap/phase-f3.md), не этот ADR.

## Контекст

Пользователь ведёт проект из постоянного чата `Kodo · Диспетчер задач` в T3 Code и хочет видеть работу воркеров отдельными чатами. Видимые чаты создаёт только сам хост своим инструментом `delegate_task`; у Kodo CLI нет доступа к инструментам хоста, а универсального desktop-бэкенда чатов нет. При этом проверка, интеграция и приёмка должны оставаться в Kodo, чтобы чат не мог объявить задачу принятой без доказательств.

## Решение и альтернативы

| Выбор | Альтернатива и причина отказа | Последствие |
| --- | --- | --- |
| Pull-протокол: `next-wave` выдаёт брифы, `complete-task` принимает SHA коммита | CLI вызывает инструменты T3 (MCP, база клиента, скрытый API): нет поддерживаемого механизма, правка баз клиента запрещена | Чаты создаёт и архивирует главный чат; Kodo только резервирует, проверяет и вливает |
| Резерв попытки с actor `project-external:<host>` и Run с `executor: {kind:'external', host}` | Общий резерв для `drain` и хоста: два исполнителя одной задачи | Владелец резерва однозначен: `drain` не исполняет внешние попытки, другой хост их не подхватывает; повтор `next-wave` возвращает те же брифы |
| Один worktree на задачу: Kodo создаёт его на ветке `kodo/<runId>` от головы интеграционной ветки, чат работает по абсолютному `brief.worktree` с `isolation: "shared"` | Хост создаёт свой worktree (`isolation: "worktree"`): второй checkout с другой базой, коммит вне ветки попытки | База попытки известна Kodo; `complete-task` сверяет ветку, чистоту и потомство коммита |
| Проверка в `complete-task`: коммит в ветке попытки, без симлинков, в `writePaths`, без секретов, затем `task-fast` и behaviour gate | Доверять отчёту чата о проверках | Дефект воркера даёт `checks_failed` с кодом; попытка остаётся `running` до нового SHA или `--abandon` |
| Все переходы — через один production-authorizer `createProjectTransitionAuthorizer`, тот же, что у `drain` | Отдельный авторизатор хоста: расхождение правил приёмки | Внешний Run проверяется как любой Run задачи волны; `accepted` даёт только gate Run |
| Мутации под lease `project:<id>` | Параллельные контроллеры с CAS без lease: гонки резерва и интеграции | Во время `drain` pull-команды отвечают `project_busy` |
| Хосты `t3` и `orca` из `PULL_HOSTS` | Протокол под один хост | Orca использует тот же протокол, но не проверялась |

## Почему CLI не вызывает инструменты T3

Инструменты хоста доступны только модели внутри чата хоста. Вызов из CLI потребовал бы неподдерживаемого канала (чтения или записи базы клиента, обхода разрешений), что запрещено правилами проекта и сделало бы Kodo зависимым от внутренностей клиента. Pull-протокол оставляет каждой стороне её роль: главный чат — создание, ожидание и архивирование видимых чатов; Kodo — состояние, проверки и интеграцию. Алгоритм главного чата описан навыком [`kodo-project-director`](../../skills/kodo-project-director/SKILL.md).

## Ограничения

- Rebase внешней задачи на новую голову ветки не поддерживается: конфликт интеграции разрешается `--abandon` и `next-wave --retry-failed`.
- Kodo не знает id чатов хоста и не может проверить, что чат архивирован; это ответственность главного чата.
- Бриф содержит абсолютный путь worktree и пути интерфейсов; state home и артефакты Run в него не попадают.
- Доставка (push, PR, merge, release) — у координатора, не у воркеров и не у протокола.
