# ADR-0014: волновая фабрика проектов

Статус: решение этапов F1–F3. Приёмку этапа фиксирует [отчёт](../kodo-roadmap/phase-f3.md), не этот ADR.

## Контекст

Project Director ([ADR-0008](0008-project-director.md)) исполнял задачи по одной: каждый Task Run проходил полный набор проверок и ревью и только после приёмки открывал зависимые задачи. Для проекта из десятков задач это медленно, а проверка каждой задачи в отрыве от соседей не ловит дефекты их сочетания. Кроме того, ProjectSpec писали вручную: правила Волны 0, непересекающихся путей и размера задачи нигде не проверялись до исполнения, а добавить новую фичу в принятый проект было нельзя.

## Решение и альтернативы

| Выбор | Альтернатива и причина отказа | Последствие |
| --- | --- | --- |
| Необязательное `execution: {cadence:'wave', integration:'branch'}` у ProjectSpec и Project | Отдельный тип проекта или новый Store: второй атомарный контур и дубли схем | Проект без `execution` даёт прежние байты spec, событий и команд (golden-хэши); legacy-путь не меняется |
| Интеграционная ветка `kodo/project/<id>`; задачи вливаются merge-коммитами по одной под lease `project-integration:<id>` | Сливать в основную ветку пользователя или копить diff: чужой checkout меняется, конфликты всплывают поздно | Checkout пользователя не трогается; следующая волна стартует от головы ветки, уже содержащей предыдущую |
| Зависимость в wave удовлетворена статусом `integrated` | Ждать `accepted`: гейт эпика сериализовал бы весь проект | Волны идут без ожидания гейтов; принятие остаётся за гейтом |
| Задача — профиль `task-fast` (быстрые проверки в quick); один gate Run на эпик, захватывающий майлстоун и проект, когда их остальные дети уже приняты | Полный набор проверок и ревью на каждую задачу: стоимость растёт линейно, а сочетание задач не проверяется | Полные проверки, ревью и smoke — один раз на эпик на реальном объединённом head; ремонт ограничен `writePaths` покрытых задач |
| Binding гейта `{gateId, runId, baseSha, headSha, mergesHash}` и правило голов: гейт ставится только на текущую голову ветки, ремонт — потомок `gate.headSha`, возврат — `mergeBackGate` с `expectedHead`, приёмка проекта — только на голове ветки | Доверять порядку кода или квитанции задачи | Сдвиг ветки после резерва даёт явный блокер (`gate_head_stale`, `wave_project_head_mismatch`), а не приёмку непроверенного head |
| `appendMilestone {milestone, epics, tasks}` — единственный способ добавить работу в принятый wave-проект | Редактировать spec или вставлять задачи под принятыми родителями: прошлая приёмка теряла бы смысл | Закрытые записи не меняются, доказательства проекта переносятся в `reopened[]`, проект снова `running` |
| Файловый чертёж `.kodo/blueprint/` (PROJECT.md, interfaces/*.md, spec.json) и детерминированная компиляция в ProjectSpec | Kodo сам режет задачи или чертёж хранится только в Store: правку невозможно увидеть и проверить до регистрации | Чертёж читается человеком и моделью; findings возвращаются главному чату, Kodo задачи не переписывает |
| Обязательная Волна 0 (`foundation`), непересекающиеся `writePaths` параллельных задач, ≤12000 байт входа задачи (`split_required`) | Проверять это в рантайме: конфликт обнаружился бы после затраченных сессий | Ошибки чертежа ловятся до создания проекта |
| Интерфейсы — неизменяемые конверты evidence в Kodo home со ссылкой по sha256 | Ссылаться на файл в репозитории: файл можно изменить после компиляции | Задачи получают проверяемые Ref; изменение интерфейса требует нового чертежа |

Заимствованные паттерны eve.dev — только как идеи, без зависимости от его рантайма, без его API и без сторонних API моделей:

- **filesystem-first** — чертёж и контекст-пакеты лежат файлами, Store хранит только проверенный результат;
- **инструкции ролей по требованию** — короткий профиль роли (`runtime/worker-roles.mjs`) попадает только в бриф задачи этой роли;
- **lead → workers** — главный чат планирует и раздаёт работу, воркеры получают ограниченный бриф и возвращают коммит;
- **durable pause** — пауза, резервы попыток и гейтов живут в Store; прерванный процесс продолжает с того же места без двойного исполнения.

## Ограничения

- Задачи всегда идут в режиме quick; ремонт в гейте требует standard/deep и `repairRounds ≥ 2`.
- `released` и доставка wave-проекта не поддерживаются (`project_wave_delivery_unsupported`); доставку делает координатор.
- Сдвиг ветки после резерва гейта проекта оставляет проект `integrated`; отдельного восстановления нет.
- Чертёж и контекст-пакет — данные, не доказательства: Ref на интерфейс фиксирует байты, а не их корректность.
- GPT и Claude — только подписочные клиенты; ключи не попадают в чертёж, брифы и логи.

## Что отложено

Гейт уровня проекта для восстановления после `wave_project_head_mismatch`, замена устаревшего неустановленного резерва гейта, доставка и релиз волнового проекта, rebase внешней задачи на новую голову ветки.
