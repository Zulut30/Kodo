# Durable jobs: очередь заданий с арендами и однократной интеграцией

Задание (job) — одна ограниченная единица работы worker, результат которой координатор интегрирует отдельно и не более одного раза. Очередь живёт в SQLite состояния Kodo рядом с Project Director и legacy Run и переживает перезапуск процесса. Решения описаны в [ADR-0009](decisions/0009-durable-jobs.md).

**Статус.** Контракты, хранилище, планировщик и read-only CLI реализованы. Engine исполняет узлы плана через эту очередь, если в `kodo.config.json` проекта задано `"scheduler": "durable"`; без этого ключа работает прежний диспетчер, и очереди не создаются. Project Director по-прежнему ведёт одну Task/Attempt за вызов: каждая Attempt — это Run, и её узлы идут через очередь при включённом флаге.

## Состояния

```
queued → running → verifying → integrating → integrated
            │  ↘ waiting_quota → running
            ↘ queued (повтор) / failed / blocked / cancelled
```

| Состояние | Смысл |
| --- | --- |
| `queued` | Ждёт допуска |
| `running` | Исполняется worker под арендой с heartbeat |
| `waiting_quota` | Пауза по квоте провайдера; scope удержан, слот свободен |
| `verifying` | Результат записан, ждёт интеграции; повторно не исполняется |
| `integrating` | Координатор интегрирует; слот интеграции один на очередь |
| `integrated` | Результат интегрирован, квитанция записана |
| `blocked` | Ждёт внешнего решения: сбой зависимости, неподключённый host, конфликт интеграции, исчерпанные квоты |
| `failed` | Исполнение исчерпало retry policy |
| `cancelled` | Отменено |

## Правила допуска

Задание стартует, только если выполнено всё:

1. Каждая зависимость `integrated`. Завершённая, но не интегрированная зависимость не считается.
2. Host доступен. Неподключённый `t3`/`orca` даёт `blocked`, а не нативный запуск.
3. Worker предлагает требуемые `capabilities` и `requiredTools`.
4. Нет пересечения с начатыми и ещё не интегрированными заданиями: ни его `writePaths` с их `writePaths`, ни его `readPaths` с их `writePaths`, ни общих `locks`.
5. Есть свободный слот: `workers` (1–8) и, если задан, лимит подписочного `pool` (0–8).

Порядок: сначала задания, у которых закончилась пауза по квоте, затем `priority` плюс число проигранных claim, затем возраст. После 8 проигрышей готовое задание резервирует свои scopes и locks: конфликтующая с ним новая работа ждёт. Резервирует только задание, которое само может стартовать: закрытый pool, неподключённый host или отсутствие нужного worker резерва не дают.

## Восстановление

| Событие | Что происходит |
| --- | --- |
| Аренда истекла (процесс умер) | Задание возвращается в очередь; при исчерпании попыток — `failed: lease_lost`. Старый worker получает `job_lease_lost` и его результат отбрасывается |
| Worker бросил ошибку | Повтор в пределах `retry.maxAttempts` (1–5, по умолчанию 2), иначе `failed`; `retryable: false` — сразу `failed` |
| Квота | `waiting_quota` до `retryAt` с сохранённым `checkpoint`; попытка не расходуется; не более 12 пауз. Scope и locks удерживаются до фактического возобновления, даже если после `retryAt` задание ещё не может стартовать |
| Результат не принят хранилищем | Не объект, больше 64 КБ или содержит секрет: задание сразу `failed: result_rejected:<код>`, очередь продолжает работу |
| Сбой между записью результата и интеграцией | Задание остаётся `verifying` и интегрируется после перезапуска без исполнения |
| Сбой во время интеграции | Задание остаётся `integrating`. После истечения аренды оно возвращается первым с `recovery: true`: координатор сверяет, попал ли merge, и только записывает квитанцию либо повторяет интеграцию того же результата (не более 3 раз) |
| Остановка координатора | Исполняемые задания возвращаются в очередь без расхода попытки |
| Отмена | `queued`/`running`/`verifying` → `cancelled`. Во время интеграции отмена только помечается: merge мог уже состояться |
| Сбой зависимости | Зависимые каскадно `blocked: dependency:<key>` и автоматически возвращаются после `retry` |

## Engine: узлы плана как задания

```json
{ "scheduler": "durable" }
```

Ключ необязателен; допустимы `"legacy"` (то же, что отсутствие) и `"durable"`. Значение сохраняется в Run при создании и не меняется при `resume`.

При `durable` каждый узел плана становится заданием очереди `run:<runId>:<хэш плана>`: `key` — id узла, `dependsOn` и `writePaths` — из плана. Очередь решает, что может стартовать и что интегрируется; работу выполняет прежний код Engine (routing, worktree, сессии, `repairRounds`, merge). Что меняется по сравнению с прежним диспетчером:

- узлы с пересекающимися `writePaths` идут по очереди до интеграции первого, а не только до конца его сессии;
- состояние узлов видно через `kodo jobs list --queue run:<runId>:<хэш>` и переживает перезапуск как очередь;
- сбой сразу после merge сверяется при перезапуске по состоянию узла и не приводит к повторному merge.

Что сохранено: лимит `concurrency` (1–5), бюджет ремонтов узла, пауза по квоте (`waiting_limits` с `retryAt`), отмена и `--retry-failed`. Попытки задания не дублируют `repairRounds`: у задания одна попытка, ремонты считает Engine.

- **Запрет параллельности.** Узел, который план (`parallel: false`) или Jev пометил как не параллельный, исполняется один от начала попытки до интеграции своего результата. Следующий узел всегда стартует от уже интегрированного результата.
- **После первого сбоя** ни одна новая сессия не стартует. Узлы, уже принятые очередью, но ещё не начавшие сессию, возвращаются в очередь без расхода попытки (`queued: handed_back`). Начатая попытка дорабатывает; следующую попытку ремонта узел не начинает. Готовые результаты интегрируются.
- **Узел, остановленный бюджетом ремонтов,** при обычном `resume` сообщается как блокер сразу, до любых сессий других узлов.
- **Потеря аренды задания** без запрошенной отмены останавливает запуск как `lease_lost` (`blocked`), а не как отмену.
- **Замена плана** отменяет незавершённые задания прежней очереди (`cancelled: plan_replaced`).

При входе в исполнение Engine владеет эксклюзивной арендой Run, поэтому аренды заданий предыдущего процесса снимаются сразу (`takeOver`), без ожидания TTL. Источник истины о прогрессе узла — состояние узла в Run; задание никогда не опережает узел.

Пауза по квоте соблюдает `retryAt`: `resume` раньше этого времени сессию не запускает и снова возвращает `waiting_limits`. Если провайдер времени не сообщил, пауза равна минуте.

## API

```js
import { Store } from './runtime/store.mjs';
import { openJobStore } from './runtime/job-store.mjs';
import { runJobQueue } from './runtime/job-scheduler.mjs';

const jobs = openJobStore({ store: new Store() });
jobs.enqueue('project:demo', [
  { key: 'api', role: 'developer', writePaths: ['src/api'] },
  { key: 'docs', role: 'documentation', writePaths: ['docs/api.md'], dependsOn: ['api'] },
]);
const summary = await runJobQueue({
  jobs,
  queue: 'project:demo',
  owner: 'coordinator',
  limits: { workers: 2, pools: { codex: 1 } },
  execute: async (job, { signal }) => ({ headSha }), // изолированный worker
  integrate: async (job, { confirmOwnership }) => {
    confirmOwnership(); // прямо перед необратимым шагом: бросает, если аренда потеряна
    return { commit };
  }, // только координатор
  reconcile: async job => ({ integrated, receipt }), // попал ли прерванный merge
});
```

Необязательный `paused: () => boolean` останавливает старт новых заданий: начатые завершаются и интегрируются. Порт `execute` может вернуть задание в очередь без вердикта и без расхода попытки, отклонив его с `handBack: true`. `jobs.takeOver(queue)` снимает аренды прежнего владельца сразу; вызывать его можно только под внешней эксклюзивной арендой всей очереди.

`summary.status`: `integrated`, `waiting_quota` (с `retryAt`), `blocked`, `stalled` (с причинами), `busy` (работа принадлежит другому процессу или ждёт сверки), `stopped` или `empty` (в очереди нет заданий, например из-за опечатки в имени). Сбой задания не превращается в успех и не бросает исключение. Исключение означает одно из двух: интеграция с неизвестным исходом или `job_integration_ownership_lost` — порт завершил интеграцию уже после того, как задание перехватил другой владелец, и возможен дубль.

Аренда не может остановить внешний merge, который уже выполняется. Если координатор завис дольше TTL аренды интеграции, второй координатор может решить по `reconcile`, что merge нет, и интегрировать сам. `confirmOwnership()` сужает это окно, но не закрывает его; единственность координатора проекта обеспечивает аренда `project:<id>`.

`enqueue` идемпотентен по `key`: тот же запрос возвращает существующее задание, изменённый — `job_idempotency_conflict`. Спецификации, результаты и квитанции с настроенными секретами отклоняются; тексты ошибок редактируются.

## CLI

```powershell
kodo jobs list [--queue QUEUE] [--json]   # очереди или задания одной очереди
kodo jobs status JOB_ID [--json]          # одно задание и последние 50 событий
```

Если в базе остались кадры WAL без файла общей памяти (писатель умер), отчёт отказывается работать (`jobs_blocked`) и не создаёт недостающий файл: восстановление выполняет только писатель.

Команды только читают. Они открывают базу в режиме read-only: не создают каталог состояния и таблицы, не выполняют миграцию, не берут блокировку записи, не захватывают задания и не пишут события. Если таблиц jobs ещё нет, отчёт пуст.

Для задания в очереди `waitingFor` показывает причину, видимую из самой очереди: зависимости, scopes и locks (`dependency_pending:api`, `scope_conflict:api`, …). Доступность host, capabilities worker и лимиты знает только координатор, поэтому отчёт их не выдумывает. Токены аренды и `payload` не печатаются.

```powershell
node scripts/run-tests.mjs tests/job-contracts.test.mjs tests/job-store.test.mjs tests/job-scheduler.test.mjs tests/job-cli.test.mjs tests/job-git-chain.test.mjs tests/job-concurrency.test.mjs tests/engine-jobs.test.mjs
```

Fixtures управляемые: fake providers с барьером на 1/2/4/8 слотов, четыре процесса на одной базе и одна настоящая цепочка Git + SQLite с worktree на задание. `tests/engine-jobs.test.mjs` прогоняет настоящий Engine с fake provider через очередь: порядок зависимостей, перекрытие, общий файл, квоту, исчерпанный бюджет, остановку и сбой после merge. Это offline evidence. Утверждений о реальном ускорении, работе подписочных клиентов или числе реально работавших агентов оно не даёт.
