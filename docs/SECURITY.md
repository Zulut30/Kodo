# Ключи и границы доверия Kodo

Координатор Kodo использует ключи Gemini, TypeSafe, Scrape.do, Reddit API и GetXAPI. Он не добавляет их в проект, планы, промпты, аргументы рабочих сессий и артефакты. Окружение рабочих клиентов и команд проверок очищается от ключей, токенов, паролей, настроек API и переменных `KODO_*`. Журналы и сохранённое состояние проходят редактирование известных значений секретов.

## Хранение

В Windows хранилище находится в `%LOCALAPPDATA%\Kodo-Credentials\credentials.dpapi.json`. Содержимое зашифровано Windows DPAPI в области `CurrentUser`; ACL каталога и файла разрешает доступ только текущему пользователю и `SYSTEM`. Шифрование и расшифрование выполняются локальным PowerShell без профиля: значения передаются через закрытые каналы stdin/stdout, а аргументы процесса содержат только постоянный скрипт. Ошибки не включают содержимое этих каналов.

В Linux хранилище находится в `$XDG_CONFIG_HOME/kodo/credentials/credentials.json`, по умолчанию `~/.config/kodo/credentials/credentials.json`. Каталог имеет права `0700`, файл — `0600`. Это защита правами файловой системы; содержимое файла не зашифровано. `KODO_CREDENTIAL_HOME` переопределяет каталог ключей на обеих системах.

Состояние запусков хранится отдельно: `%LOCALAPPDATA%\Kodo` в Windows и `~/.local/state/Kodo` в Linux; `KODO_HOME` переопределяет этот каталог. Новые рабочие деревья по умолчанию находятся в `%LOCALAPPDATA%\Kodo-Worktrees` или `$XDG_STATE_HOME/Kodo-Worktrees` (`~/.local/state/Kodo-Worktrees`). Их расположение задаётся через `KODO_WORKTREE_HOME`. Старые активные деревья сохраняют записанный путь для продолжения работы. Каталог ключей следует размещать вне Git-проектов и рабочих деревьев.

При первом чтении Kodo автоматически переносит старый `<KODO_HOME>/secrets.json`. Он сначала записывает защищённое хранилище, повторно читает его и сравнивает все переносимые ключи. Только после успешной проверки и проверки отсутствия изменений исходного файла удаляется старый открытый JSON. Ошибка защиты, повреждённые данные или разные значения одного ключа сохраняют исходный файл и останавливают миграцию. Повторный запуск использует уже проверенное хранилище.

Координатор также принимает `KODO_GEMINI_API_KEY`, `KODO_TYPESAFE_API_KEY`, `KODO_SCRAPEDO_TOKEN`, `KODO_REDDIT_API_KEY`, `KODO_GETX_API_KEY` и одноимённые переменные без префикса `KODO_`. Значение с префиксом имеет приоритет, затем обычное окружение, затем хранилище. Значения из окружения автоматически на диск не записываются. Авторизацией подписок Codex и Claude Code управляют сами официальные клиенты; Kodo не преобразует эти запуски в API-вызовы.

## Доверенные локальные клиенты

Исполнители Kodo — доверенные локальные клиенты, работающие от имени пользователя. Выполняемые ими команды `Bash`/PowerShell, тесты и зависимости проекта могут обращаться к ресурсам этого пользователя. Ограничение области изменений, отдельное рабочее дерево и очистка окружения уменьшают случайное раскрытие данных, но не обеспечивают изоляцию произвольного кода от файлов компьютера.

DPAPI защищает ключи на диске от чтения другими пользователями и копирования на другой компьютер. Процесс того же пользователя обычно может вызвать DPAPI и расшифровать данные; Unix-права также не блокируют процессы владельца. Поэтому Kodo не обещает защиту ключей от вредоносного кода, запущенного тем же пользователем. Для недоверенных проектов требуется отдельная учётная запись или внешняя изолированная среда с собственными правами доступа. Ключи координатора рабочим агентам не нужны и не должны запрашиваться ими.

## Приватные evidence и RTK

Engine сохраняет полные данные analysis/research, node contracts, review/diff и command stdout/stderr после redaction известных секретов вне Git, в `runs/<runId>/evidence/`. Сводка строится из того же снимка. Content-addressed JSON включает base/head; ссылки несут hash/bytes/head. На POSIX каталоги закрыты `0700`, файлы evidence — `0400`; на Windows owned evidence/worker directories получают защищённый ACL текущего пользователя и SYSTEM, без изменения subscription homes. Символьные ссылки и пути внутри Git-репозитория отклоняются. Это защита локального хранения, а не sandbox от кода того же пользователя.

Engine проверяет hash/head полных evidence до и после native-сессии, а check logs — также перед reuse успешных checks. Повреждение или исчезновение блокирует работу с `evidence_integrity`, сохраняя unfinished worker state без автоматического code repair/research. Сокращённый prompt с явными omissions не скрывает failed/skipped/unknown и не заменяет полные диагностические данные. Старый check без полного `outputPath` остаётся историческим отрывком. [Контракты и границы](EFFICIENCY.md).

Managed RTK OSS 1.1.0 разрешён только для явного поддерживаемого human-readable worker output. Проверка inventory выполняется после subscription lease, результат переиспользуется в одной сессии и проверяется заново в следующей. Private tracking DB располагается в отдельном `worker-tools/rtk-*` вне Git, `RTK_RECALL=0`, `RTK_TEE=0`, `RTK_TELEMETRY_DISABLED=1`; inherited RTK overrides удаляются перед назначением безопасных. HOME/USERPROFILE/auth не перенаправляются. RTK может читать global config, но Kodo не вызывает init/config-save и не изменяет его. Global RTK 0.50.0, hooks и пользовательская tracking DB не заменяются.

RTK не применяется к JSON/protocol/porcelain/NUL, Node/TAP, scanners, UI receipts, CI или delivery. Утрата actionable errors требует raw-повтора с полным redacted evidence и не считается экономией. Установка и live probes остаются у координатора; отсутствующий/неподдерживаемый RTK использует raw commands. API/proxy fallback для GPT/Claude не добавляется. [RTK pins и guidance](UI-TOOLS.md#rtk-и-вывод-shell).

## Локальные security gates

```json
{
  "security": {
    "enabled": true,
    "autoInstall": true,
    "tools": ["semgrep", "gitleaks"]
  }
}
```

Без настройки `enabled:false`, `autoInstall:true`, `tools:["semgrep","gitleaks"]`. Сам Kodo явно включает оба сканера. Можно выбрать один. Необязательный `semgrepConfig` — относительный локальный `.yml`/`.yaml` внутри проекта; без него используются `runtime/security-rules.yml`. Remote registry, include/extends, secret validators и SCA не поддерживаются. Локальные правила ищут ограниченный набор опасных exec/eval-паттернов JS/Python; это не полная сертификация безопасности.

`runSecurityChecks` проверяет чистый неизменный Git head и байты tracked source, включая runtime и tests; исключены `.git`, зависимости/генерируемые каталоги и закреплённые upstream references. Symlink source и неполный scan блокируют результат. Semgrep работает на закрытой копии текущих исходников, с metrics/version checks off, без uploads и пользовательских ignore-послаблений. Gitleaks использует `--redact=100`; отсутствие findings требует корректного завершённого JSON, не просто exit 0. Квитанция различает наблюдаемое покрытие Semgrep и supplied scope Gitleaks.

История Gitleaks включается только явно: `"history":{"baseSha":"<полный SHA предка проверяемого HEAD>","maxCommits":50}` внутри security. Допустим бюджет 1–100, по умолчанию 50; проверяется только диапазон `baseSha..headSha`, вместе с текущими файлами. Слишком длинный диапазон блокируется, а не обрезается молча. Значение SHA нужно заменить настоящим commit.

Findings сохраняют только `ruleId`, `file`, `line`, `severity`; `Secret`, `Match`, snippets и raw stderr не экспортируются. Ошибки scanner, timeout, malformed JSON, отсутствие файла/бинарника или нулевое/неполное покрытие не могут считаться чистым результатом. Receipts привязаны к head/config/pins, source/rules hashes и байтам evidence. Изменённые исходники или rules делают их неактуальными. Приватные отчёты находятся вне Git, а generated scanner homes удаляются штатной ограниченной процедурой.

На Windows Semgrep 1.183.0 требует короткого собственного OS-temp для IPC: длинный вложенный TEMP вызвал реальную RPC-ошибку на чистой fixture. Адаптер выделяет свой короткий временный каталог и передаёт его только scanner через `TEMP`/`TMP`/`TMPDIR`. Глобальный TEMP и службы WSL не изменяются. [Фактическое live evidence](VALIDATION.md#реальные-квитанции-run9fc).

## UI и приватность

Координатор запускает только собственный Chrome/CDP и временные профили, либо работает с явно указанным desktop app/window. Личный профиль и чужие endpoint не присваиваются при ошибке. Страница, goal, история и результаты инструментов — недоверенные данные. Модельный DONE или успешный summary недостаточны: нужны независимые DOM/accessibility assertions.

Ключ Google получают только Browser Use/Vibetest/Jev bridges, TypeSafe — только Jev. Окружение запуска приложения/Chrome и worker-сессии этих ключей не содержит. OpenAI/Anthropic/DeepSeek/Browser Use Cloud fallback отсутствует. Chrome MCP отключает usage statistics, performance CrUX и update checks; Browser Harness/Jev запускаются без записи. Сырые snapshots/traces и временные профили не коммитятся; structured receipts редактируются и ограничиваются. [Полный UI-контракт](UI-TOOLS.md).

`progress.md` содержит только ограниченную сводку переходов/проверок из SQLite, без сырых промптов. Видимые worker-чаты архивируются только после проверенного завершения и только средствами host-клиента; постоянный диспетчер и чужая история сохраняются. Архивирование не является постоянным удалением, внутренние базы Codex/Claude не редактируются.
