# Сторож прогресса и текущий блокер

Этап 10 отвечает на два вопроса: движется ли запуск и что именно мешает ему сейчас. Решения описаны в [ADR-0012](decisions/0012-progress-watchdog.md).

Сторож только наблюдает и останавливает. Код, план и доставку он не меняет.

## Что считается прогрессом

Прогресс — изменение принятого критерия между двумя раундами проверки:

| Причина | Факт |
| --- | --- |
| `node_integrated` | Интегрирован ещё один узел плана |
| `check_passed` | Больше команд проверки завершилось с кодом 0 |
| `behavior_gate_passed`, `behavior_findings_resolved` | Behaviour gate прошёл или находок стало меньше |
| `gate_passed` | Прошёл ещё один из gates UI, security, architecture |
| `review_passed`, `review_findings_resolved` | Ревью прошло или находок стало меньше |

Новый commit, изменённый текст ошибки, число сессий, строк, токенов и вызовов инструментов прогрессом не считаются: сторож их не наблюдает.

## Настройка

```json
{ "watchdog": { "stalledRounds": 2, "rejectCosmetic": true } }
```

Блок необязателен. Без него действуют только прежние правила: одинаковая сигнатура сбоя на том же commit (`no_progress`) и бюджет `repairRounds`.

| Ключ | Диапазон | Смысл |
| --- | --- | --- |
| `stalledRounds` | 1–5, по умолчанию выключено | Остановить запуск после стольких раундов ремонта подряд без прогресса |
| `rejectCosmetic` | по умолчанию `false` | Не засчитывать узел `developer` или `tester`, который не изменил ничего, кроме пустых строк |

При `stalledRounds: 2` запуск останавливается после третьего неудачного раунда: первый задаёт точку отсчёта, два следующих не дали прогресса. Причина остановки — `no_verified_progress`. Порог — правило диагностики, а не гарантия: он не отличает трудную задачу, которая продвигается внутри одной команды проверки, от топтания на месте. Для таких задач порог поднимают или не задают.

Прогресс считается относительно лучшего достигнутого состояния, а не предыдущего раунда. Раунд, который сломал проверку, и следующий, который её починил, прогрессом не являются: запуск лишь вернулся туда, где уже был.

Эффективный бюджет ремонтов по-прежнему ограничен профилем режима: 1 для `quick`, 3 для `standard`, 5 для `deep`. Поэтому порог имеет смысл только ниже бюджета: при `standard` действует лишь значение 1, при `deep` — значения 1–3. Больший порог срабатывает не раньше исчерпания бюджета.

Состояние сторожа (`run.watchdog`) сохраняется вместе с запуском: счётчик переживает перезапуск процесса и паузу по квоте. Шаг с тем же ключом раунда повторно не считается. Обычный `resume` остановленного запуска новых раундов не даёт; новый отсчёт начинает только явный `--retry-failed`.

`rejectCosmetic` отклоняет узел, который по существу ничего не изменил. Правило намеренно узкое: проверка может пропустить косметику, но не должна принять настоящую работу за неё. Косметикой считается одно из двух:

- узел ничего не изменил;
- все изменённые файлы — обычные JS/TS (`.js`, `.mjs`, `.cjs`, `.ts`, `.mts`, `.cts`) или Python, и версии каждого файла отличаются только пустыми строками.

Файл при этом не судится, если в нём есть конструкция, которая переносит текст через конец строки: шаблонная строка (обратная кавычка) в JS/TS, строка в тройных кавычках в Python, строка, продолженная обратной косой чертой.

Всё остальное считается настоящей работой и не отклоняется:

- любая правка комментария, строчного или блочного. Комментарий может быть директивой, которую читает линтер, проверка типов, сборщик или сканер безопасности (`eslint-disable`, `nosemgrep`, `# pyright:`, `//= require`), и надёжно отличить её от пояснения нельзя. Узел, который добавил только комментарии, оценивают проверки проекта и ревью;
- добавленный, удалённый или переименованный файл, смена режима файла, бинарный файл, файл больше 1 МБ;
- любое изменение пробелов, кроме пустых строк: отступы, пробелы в конце строки, перевод строк, конец файла;
- файлы любого другого типа: JSX/TSX, shell, YAML, CSS, SQL, C, Go, Rust и прочие;
- изменение больше чем в 20 файлах;
- всё, что проверка не смогла прочитать.

Узел с ролью `documenter` не проверяется: его результатом могут быть комментарии.

## Текущий блокер

Когда запуск останавливается в состоянии `blocked` или `waiting_limits`, в `run.blocker.current` записывается, что именно его остановило:

```json
{
  "code": "no_verified_progress",
  "scope": "verification",
  "message": "Проверки не пройдены: …",
  "signature": "…",
  "firstSeen": "2026-11-10T10:00:00.000Z",
  "lastSeen": "2026-11-10T10:00:00.000Z",
  "occurrences": 1,
  "headSha": "…",
  "hypotheses": ["Several repair rounds changed no accepted criterion: …"],
  "evidence": [{ "sha256": "…", "kind": "check" }]
}
```

- `scope` — `verification`, id узла плана или `run`.
- `hypotheses` — кандидаты в объяснение, выведенные из записанных фактов (код остановки, пометка `regression` или `pre_existing`, сбой behaviour gate). Это не вердикт.
- `evidence` — хэши evidence последних проверок и оракулов; сами файлы лежат в каталоге evidence запуска.

Один и тот же блокер — это та же причина остановки в той же области на том же commit. При повторной остановке он не дублируется: растёт `occurrences`, первый текст сбоя сохраняется, последний записывается в `lastMessage`. Сводка показывает последний текст, а если он отличается от первого, то и первый (`First reported as`): повторная остановка может сообщать лишь то, что запуск остаётся остановленным. У остановки без собственной области (`run`) нет такой опоры, поэтому там в тождество блокера входит и текст: другая ошибка — другой блокер. Другой блокер переносит прежний в `run.blocker.history` (до 20 записей) с исходом `replaced`.

При каждом новом входе в запуск текущий блокер становится историей с исходом `resumed`: пока запуск работает, его ничто не блокирует. Если запуск снова остановился по той же причине на том же commit, запись возвращается из истории в текущие с увеличенным счётчиком. Сохранённая ошибка прошлой попытки (`run.error`) остаётся для совместимости, но текущим блокером не считается. При успехе текущего блокера нет.

Область и причину блокера называет сама ошибка остановки, а не последняя сохранённая оценка координатора: при двух одновременно остановившихся узлах блокер относится к тому узлу, чья ошибка остановила запуск. Хэши вывода проверок и оракулов прикладываются только к остановке на проверке, включая остановку behaviour gate.

## Сводка восстановления

`progress.md` в каталоге запуска показывает:

```
Current blocker: no_verified_progress [verification] Проверки не пройдены: …
Seen 1 time(s): first …, last …; commit …
- Hypothesis: Several repair rounds changed no accepted criterion: …
Evidence: check <sha256>
Earlier blockers: 1
- resumed 2026-11-10T11:00:00.000Z: quota [run] …
Watchdog: 2 round(s) without verified progress; stopped at limit 2
```

Пока идёт продолжение запуска, старая ошибка выводится строкой `Last error (previous attempt, not the current blocker)`. Отменённый запуск показывает `Stopped`, с записью блокера или без неё. Строка `Watchdog` выводится, только если порог задан или сработал. Запуски, сохранённые до этапа 10, по-прежнему показывают `Pending blocker`.

`kodo status RUN_ID` печатает сохранённый запуск целиком, включая `blocker` и `watchdog`.
