# Project Director: offline backlog и foreground execution

MVP06 добавляет durable `Project → Milestone → Epic → Task → Attempt` рядом с legacy Run. SQLite Kodo остаётся источником состояния; `status` — ограниченная сводка, не доказательство приёмки. Реализация интегрирована локально; общая приёмка06 ещё pending. [Статус и evidence](kodo-roadmap/phase-06.md), [ADR-0008](decisions/0008-project-director.md).

## CLI и конфигурация

Нужны Node.js 24 и существующий owned абсолютный `root`; для выполнения — Git с исходным commit и настроенный проект. В исходном checkout заменяй `kodo` на `node <путь-к-Kodo>/cli/index.mjs`.

```text
kodo project create --file SPEC [--command-id UUID] [--json]
kodo project status PROJECT_ID [--json]
kodo project plan PROJECT_ID [--limit 1..24] [--dry-run] [--json]
kodo project resume PROJECT_ID [--retry-failed] [--command-id UUID] [--json]
kodo project drain PROJECT_ID [--max-waves 1..100] [--concurrency 1..5] [--retry-failed] [--command-id UUID] [--json]
kodo project cancel|pause PROJECT_ID [--command-id UUID] [--json]
kodo project reprioritize PROJECT_ID TASK_ID --priority 0..100 [--command-id UUID] [--json]
kodo project approve-risk PROJECT_ID TASK_ID --reason TEXT [--command-id UUID] [--json]
```

`PROJECT_ID` — возвращённый UUID, а `Task.id` — slug. Лишние/повторные флаги и аргументы отклоняются до чтения credentials/state. JSON имеет форму `{schemaVersion:1, projectId, revision, result}`. Exit0 означает успешное выполнение команды, exit1 — invalid input, exit2 — blocked/неуспешное foreground выполнение. Ошибки содержат только безопасные постоянные коды. Успешный `status` не означает accepted; `plan` возвращает exit2 при пустом `taskIds`, даже если все задачи уже завершены.

`plan` всегда dry-run, с флагом `--dry-run` и без него: не резервирует Attempt и не запускает Engine. Команды offline/control не открывают provider sessions. Они лениво создают Project composition и могут инициализировать Store/миграцию: это не обещание filesystem read-only. Coordinator-only known values загружаются перед hash/write/output; нужны явные отдельные `KODO_HOME` и `KODO_CREDENTIAL_HOME` для безопасной проверки примеров.

Project CLI **не принимает** `--project`, `--mode`, `--model` и `--prepare`; `--concurrency` принимает только `drain` волнового проекта. Root берётся из ProjectSpec. `executionMode`, `client`, `primaryModel`, разрешённые `models`, команды, gates и delivery задаются в `<root>/kodo.config.json`, по [правилам runtime](RUNTIME.md#режимы-исполнения). Режим исполнения quick/standard/deep не является игровым форматом Standard/Wild/Battlegrounds. Пример отдельного ограничения для offline planning:

```json
{"schemaVersion":1,"client":"codex","executionMode":"quick","maxTasks":1,"researchBudget":0,"repairRounds":1,"concurrency":1}
```

Это не готовый execution config: перед `resume` нужны реальные обязательные test/build команды и настройки gates/delivery целевого проекта. GPT/Claude исполняются только через авторизованные подписочные клиенты. Ключи остаются у координатора вне Git, ProjectSpec, prompts, workers и logs; API fallback отсутствует. Сохранённые mode/model/budgets/quota/session границы существующего Run сохраняются. Новый Project retry переносит прежний режим/модель и меньшие research/repair/concurrency/maxTasks; расширение требует отдельного нового запуска.

## Формат ProjectSpec v1

Авторитетный strict parser — [project-contracts.mjs](../runtime/project-contracts.mjs), отдельного JSON Schema для Director нет. Неизвестные поля отклоняются; перечисленные поля обязательны, пустые reference arrays допустимы.

| Запись | Поля |
| --- | --- |
| ProjectSpec | `schemaVersion:1, id, root, title, definitionOfDone, constraints, businessContext, architectureRefs, milestones, epics, tasks` |
| MilestoneSpec | `id, title, acceptance, releaseRequired` |
| EpicSpec | `id, milestoneId, title, acceptance` |
| TaskSpec | `id, epicId, title, description, owner, dependsOn, writePaths, acceptance, interfaceRefs, priority, userValue, risk, estimatedEffort, riskApprovalRequired` |
| Criterion | `id, text, evidenceKinds` (непустой список) |
| Ref | `kind, runId:null\|UUID, headSha:null\|SHA, path, sha256` |
| Mapping | `criterionId, refs:[sha256], actor, reason` |

`id` — slug `[a-z][a-z0-9-]{0,47}`; родители и зависимости принадлежат одному Project, DAG не содержит циклов. `writePaths` — непустые безопасные repository-relative scopes. `priority` 0–100, `userValue`/`risk` 0–5, `estimatedEffort` — положительное safe integer. Ref kinds: `interface`, `acceptance`, `checks`, `review`, `contract`, `delivery`, `release`; path указывает на owned private immutable evidence вне Git, не на credentials. Создание записи с Ref не подтверждает её истинность.

Bounds: до1000 элементов в typed collections, глубина16 и raw safety budget32MiB. Полный обязательный task input с immutable Project context ограничен12000 UTF-8 bytes; превышение требует разделить задачу (`split_required`), а не обрезать acceptance/constraints. План выбирает горизонт1–24 с учётом меньшего mode/project cap; весь backlog не помещается в prompt одного Run. Ранжирование: critical path, priority, value, risk по убыванию, затем effort и id. Непринятые зависимости, непроверенные interfaces, отсутствие актуального risk approval, pause/control или существующая попытка блокируют выбор.

## Внутренние порты и durable boundaries

Это ESM interfaces для доверенной coordinator composition, не JSON-флаги полномочий:

| Модуль / export | Ответственность |
| --- | --- |
| `project-contracts`: `normalizeProjectSpec`, `normalizeDirectorRecord`, `directorBytes`, `directorContractHash`, `buildDirectorTaskInput`, `assertDirectorSafe`, `assertProjectTransition` | Общие схемы, порядок байтов/hash и safety; options содержат явный `knownValues` |
| `project-store`: `await openProjectStore({store,contracts,authorizeTransition})` | Возвращает `apply(command)`, `snapshot(projectId)`, `history(projectId,{after,limit})`, `installRun({binding,runDraft})` |
| `project-planner`: `planProjectHorizon({snapshot,limit,availability,now},ports)` | Чистый bounded DAG plan, `{schemaVersion,projectId,revision,taskIds,blocked,order,dryRun:true}` |
| `project-evidence`: `evaluateProjectAttempt`, `evaluateProjectTransition` | Await trusted `verifyRef`/`validateRun`; eligibility/blockers не дают права записывать terminal state |
| `project-director`: `createProjectTransitionAuthorizer({store,engine,contracts,evaluator})` | Свежая проверка фактического Run/head/config/gates/evidence перед разрешением перехода; wave-проект (`isWaveProject`) идёт в `evaluateWaveTransition`, остальные — прежним путём |
| `project-director`: `createProjectDirector({repo,engine,planner,evaluator,clock})` | `plan/run/resume/drain/cancel/pause/reprioritize/approveRisk`, переиспользование Engine; `run` wave-проекта — `project_wave_drain_required`, `resume` — `drain` одной волны |
| `project-progress`: `buildProjectProgress(snapshot)`; `project-cli`: `projectCli(argv,ports)` | Bounded counts-only сводка; strict CLI и `{report,exitCode,output}` |
| `project-director-waves`: `createWaveContext`, `selectWave`, `integrateAndAdvance`, `runPendingGates`, `drain`, `attemptExecutor`, `integrationOf` | Исполнение волнового проекта, см. «Волновой режим: исполнение» |
| `project-external`: `nextWave`, `completeTask`; `worker-roles`: `workerRole` | Pull-протокол внешних воркер-чатов, см. [T3-HOST.md](T3-HOST.md) |

Snapshot: `{schemaVersion,project,revision,milestones,epics,tasks,currentAttempts,riskApprovals,completeness}`. Каждая count-запись содержит `total/returned/complete` из одной SQL read transaction; incomplete не доказывает полноту. `currentAttempts` включает последнюю settled попытку каждой задачи; старые попытки/approvals сохранены в истории, current approvals соответствуют Task.revision. Events читаются отдельно: history возвращает `events,total,complete,nextAfter` после cursor, limit1–1000.

Command: `{schemaVersion:1,commandId,projectId,expectedRevision,actor,reason,action}`. Create использует null projectId/revision; остальные записи — CAS. Action ops: `create/insert/amend/transition/setPaused/approveRisk/reserveAttempt`; это не дополнительные CLI-команды. Идентичный command ID+payload replay возвращает прежний результат; изменённый payload отклоняется. Reprioritize меняет Task revision и тем самым инвалидирует старое risk approval; active Task не переопределяется. Immutable Project context не имеет amend в MVP.

Хранилище использует additive namespaced tables/version registry в существующем `Store.db`, без захвата `user_version` и переписывания legacy Run. Перед первой миграцией — Node24 SQLite consistent backup с WAL, затем atomic migration; резервная копия остаётся вне Git в `project-backups/migration-*`. Offline restore требует закрытых handles и защиты более новых записей. Reserve фиксирует Attempt/runId/Task revision/contractHash; install атомарно связывает полный legacy Run и binding. Повтор после crash согласует ту же reservation, не создаёт второй Run. Legacy прямые callers сохраняют прежний default I/O.

## Волновой режим: данные

Слой данных для больших проектов: задачи интегрируются в ветку волнами, а общий gate Run проверяет их вместе. Здесь описаны только данные и проверки Store. Исполнение волн принадлежит директору.

**`execution`.** ProjectSpec и запись Project принимают необязательное `execution: {cadence, integration, watchdog?}`. Допустимы только `{task, frontier}` (эквивалент legacy) и `{wave, branch}`, иначе `project_execution_unsupported`; неизвестный ключ — `project_schema`. `watchdog: {stalledRounds: 1..5|null, rejectUnchanged}` хранится как задан. Значение wave по умолчанию `{stalledRounds:2, rejectUnchanged:true}` подставляет директор при запуске. Необязательные поля пишутся после обязательных. Проект без `execution` даёт прежние байты spec, record, snapshot, events и command; это закреплено golden-хэшами в `tests/project-wave-contracts.test.mjs` и `tests/project-wave-store.test.mjs`. `buildDirectorTaskInput` и `directorContractHash` от `execution` не зависят.

**Зависимости.** `dependencySatisfied(project, status)`: для wave (`isWaveProject(project)`) — `integrated|accepted|released`, иначе — `accepted|released`. Правило используют `assertProjectTransition` (переход в ready/running) и planner (блокировка и critical path). Строки причин прежние: `dependency_not_accepted:<id>`.

**`appendMilestone {milestone, epics:[1..], tasks:[1..]}`** — единственный способ добавить работу в закрытый wave-проект. Чистая проверка `assertProjectReopen({snapshot, action})` требует:

- wave-проект в accepted|released, не на паузе, полный snapshot, все текущие попытки settled, иначе `project_append_blocked`;
- только новые id, иначе `project_identity_conflict`;
- новые эпики только под новым milestone, новые задачи только под новыми эпиками, иначе `project_parent_invalid`;
- зависимости только на новые задачи (без циклов) или на существующие accepted|released, иначе `project_dependency_invalid`. Integrated не подходит;
- граф эпиков (старые и новые вместе) ацикличен, иначе `project_epic_cycle` (см. ниже);
- новый майлстоун и каждый новый эпик непусты (в эпике есть задача), иначе `project_container_empty` с `containers: [{kind, id}]`.

**Непустые контейнеры.** Гейт эпика ставится только над его задачами, поэтому пустой эпик (и майлстоун без эпиков) навсегда остался бы `proposed`, а `drain --retry-failed` отвечал бы `wave_dependency_unaccepted`. Для wave-проекта `create` и `appendMilestone` отклоняют майлстоун без эпиков и эпик без задач (`project_container_empty`, `emptyContainers` в `project-contracts.mjs`); lint чертежа и майлстоуна сообщает об этом раньше (`blueprint_container_empty`, [BLUEPRINT.md](BLUEPRINT.md)). Legacy-проекты — без изменений.

**Ацикличность эпиков.** Гейт эпика ставится, только когда зависимости его задач вне эпика приняты, поэтому цикл зависимостей между эпиками навсегда оставил бы их `integrated` без гейтов (например, задачи `A1 → B1 → A2 → B2`, буква — эпик). Для wave-проекта при `create`, `appendMilestone` и любом изменении графа (`insert`/`amend`, проверка Store `assertGraph`) граф эпиков (ребро эпик X → эпик Y, если задача X зависит от задачи Y другого эпика) обязан быть ацикличным, иначе отказ `project_epic_cycle`; ошибка несёт `epics` — эпики цикла по порядку (`epicCycle(epics, tasks)` в `project-contracts.mjs`). Legacy-проекты не меняются.

Store в той же `BEGIN IMMEDIATE` переводит Project в running без lifecycle transition. Evidence и mappings Project переносятся в `reopened[]`: до 100 записей `{status, revision, reopenedAt, evidence, mappings}`, только у wave-записи. Так старые и новые refs не дают неоднозначного bound Run. Закрытые дочерние записи не меняются, новые вставляются proposed. Пишется одно событие `appendMilestone`, CAS и replay работают как у прочих команд. `insert` под accepted родителем по-прежнему `project_insertion_blocked`, transition accepted→running по-прежнему запрещён.

**Gate record** хранится в `kodo_project_records` с `kind:'gate'` и uuid id: `{schemaVersion, id, projectId, number, containers, runId, baseSha, headSha, merges, installed, createdAt, updatedAt, supersededBy?}`. `containers` — непрерывная цепочка от узкого контейнера к широкому: epic ⊂ milestone ⊂ project. `merges` — 1–1000 записей `{taskId, attemptId, runId, mergeCommit}`. Необязательное `supersededBy` (uuid гейта-преемника) есть только у неустановленного резерва, который заменили; без него байты записи прежние.

`reserveGate {containers, baseSha, headSha, merges, retry}` работает только для wave, иначе `project_gate_unsupported`. Цепочка должна существовать и быть открытой. Milestone или project входит в цепочку только если все его дети вне цепочки уже accepted|released на момент резервации; для milestone/project в `containers[0]` — все его дети. Так гейт эпика A не захватывает общий milestone, пока соседний эпик B открыт. `merges` покрывают ровно задачи самого широкого контейнера, каждая в integrated|accepted с текущей попыткой (`attemptId`, `runId`). Каждый `mergeCommit` сверяется с доверенным `run.integration` Run этой попытки: `status:'merged'`, тот же `mergeCommit`, `mergedHead === run.headSha`; заявленный старый или чужой коммит отклоняется. Диапазон гейта не бывает пустым: `baseSha ≠ headSha`, `baseSha` — записанный `integration.before` одного из покрытых слияний и не сам merge-коммит, а до транзакции порт `gateRange({root, baseSha, headSha, mergeCommits})` (по умолчанию Git в корне проекта, `gateRange` из `project-integration.mjs`) подтверждает, что каждое слияние лежит на first-parent истории `headSha` после `baseSha`, а у самого раннего из них первый родитель — `baseSha`. Значит, каждый `mergeCommit` — строгий потомок базы и `baseSha..headSha` содержит все покрытые слияния. Нарушение — `project_gate_invalid`. Если для `containers[0]` уже есть гейт, новый допускается, только когда (иначе `project_gate_exists`):

- последний гейт не установлен, у него нет Run и голова другая: прежний резерв устарел и в той же транзакции помечается `supersededBy`; резерв на той же голове не дублируется;
- `retry:true` и Run последнего гейта blocked/failed/cancelled;
- последний гейт — гейт проекта (`containers[0].kind === 'project'`), его Run `succeeded`, а голова другая: ветка ушла дальше проверенной головы.

Store генерирует id и runId, `number` = максимум по проекту + 1, событие `reserveGate` имеет entity `{kind:'gate', id}`.

`installGateRun({binding, runDraft})` проверяет, что `binding` байт-в-байт равен `gateBindingFor(gate)` (`{schemaVersion, kind:'gate', projectId, gateId, number, runId, baseSha, headSha, mergesHash}`, `mergesHash` — sha256 канонического JSON merges). `runDraft.task` должен совпадать с `buildGateInput({project, gate, tasks})`: префикс и компактная сводка `{schemaVersion: 2, projectId, gate: {containers, baseSha, headSha}, taskCount, manifest: {kind: 'gate-manifest', sha256, bytes}}`. Полный перечень и замороженные контракты покрытых задач в порядке merges — манифест гейта `buildGateManifest({project, gate, tasks})` → `{manifest, sha256, bytes}` (`{schemaVersion: 1, projectContext, gate, tasks}`, до 32 MiB); его SHA-256 по каноническим байтам входит в сводку. Манифест хранится неизменяемым evidence-артефактом gate Run (kind `gate-manifest`, content-addressed, как прочие конверты Run), ссылка — `runDraft.gateManifest = {path, sha256, bytes, headSha}`: файл `gate-manifest-<sha256>.json` в `<artifacts>/evidence` черновика, `headSha = gate.headSha`. Поэтому размер проекта гейт не ограничивает: 240 задач в 24 эпиках доходят до установки гейта проекта (`tests/project-wave-large-gate.test.mjs`). `runDraft.directorBinding` равен binding. Форма черновика gate Run своя (`validGateRunDraft`): поля legacy-черновика как в `installRun`, но `baseSha`/`headSha` равны гейту, ссылка на манифест, `plan.tasks` — покрытые задачи в порядке merges с их `writePaths` и `dependsOn: []`, `nodes` — ровно эти задачи `{id, attempt:0, status:'integrated', headSha: mergeCommit, sourceRunId, attemptId}`, `completed = {implementation:true}`, без `verificationProfile`/`executor` и с выключенной доставкой; иначе `project_run_draft_invalid`. Свежая установка требует, чтобы гейт был последним для своего контейнера, не был заменён (`supersededBy`) и его merges оставались текущими (с той же сверкой `run.integration`), иначе `project_binding_conflict`. Install ставит `installed` и повышает revision; повтор возвращает сохранённый Run. Штатный путь — `createGateRunDraft` ([VERIFICATION.md](VERIFICATION.md)).

Манифест гейта (`buildGateManifest`, схема 2) содержит контракты покрытых задач и `containers` — критерии приёмки покрытых контейнеров (`acceptance` эпика и майлстоуна, `definitionOfDone` проекта); вход — `{project, gate, tasks, containers: gateContainerCriteria(snapshot, gate)}`, Store при `installGateRun` пересчитывает его сам. Ревью gate Run подтверждает каждый критерий (`review.criteria`), подробно — [VERIFICATION.md](VERIFICATION.md#gate-run).

Snapshot wave-проекта содержит `gates` (все гейты по `number`) и `completeness.gates`, прочитанные в той же транзакции. У legacy-проекта этих ключей нет, а contracts отклоняют их несоответствие режиму. Progress добавляет строку `gates` только при наличии ключа. Миграция SQLite не менялась, её дайджест закреплён тестом.

## Волновой режим: интеграционная ветка и доказательства

**`runtime/project-integration.mjs`.** Ветка `kodo/project/<projectId>` живёт в собственном worktree `<worktreeHome>/project-<projectId>/integration` вне checkout пользователя (`ensureIntegration`); ветку и HEAD пользователя Kodo не трогает. `mergeTask` вызывает `savePending({before})` до слияния, сливает голову задачи `--no-ff` с сообщением `Kodo: integrate <taskId>`, проверяет родителей (`HEAD^1 = before`, `HEAD^2 = голова задачи`) и что diff слияния лежит внутри writePaths задачи; конфликт → `merge --abort` и `project_integration_conflict`, выход за writePaths → откат и `project_integration_scope`. Повтор после сбоя восстанавливает уже сделанное слияние и заново проверяет scope. Перед любым новым слиянием (`mergeTask` и `mergeBackGate`) worktree должен быть чистым и без незавершённой Git-операции: `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply`, `sequencer`, `BISECT_LOG` (пути — `git rev-parse --git-path`, они свои у каждого worktree). Пустой `git status` этого не доказывает: слияние или cherry-pick без итоговых изменений оставляет `MERGE_HEAD`/`CHERRY_PICK_HEAD` при пустом статусе. Повтор после сбоя до merge commit получает в `pending` значение, сохранённое `savePending` (`{before}`): если единственная незавершённая операция — `MERGE_HEAD`, `HEAD = pending.before` и `MERGE_HEAD = taskHead`, это наше слияние — `git merge --abort` и слияние заново. Любое другое состояние — чужое слияние, повтор без `pending`, несовпадающий `pending`, другая операция, а в `mergeBackGate` любая незавершённая операция — сразу `project_integration_worktree_invalid` без `merge --abort`, `savePending` и нового `git merge`; чужое состояние не трогается. `merge --abort` выполняется только для своего подтверждённого незавершённого слияния и для собственного слияния, упавшего на конфликте. Сериализацию слияний (lease `project-integration:<id>`) держит вызывающий. `waveFrontier` возвращает голову ветки и требует, чтобы все переданные merge-коммиты были её предками (`project_frontier_integration_missing`). Worktree принимается только по этому каноническому пути (сравнение по realpath): если ветка открыта в любом другом checkout (linked worktree пользователя, в том числе рядом с каноническим после `git switch --ignore-other-worktrees`), `ensureIntegration` до любых Git-операций отказывает `project_integration_branch_busy` и чужой HEAD не трогает; проверяются все записи `git worktree list --porcelain` с этой веткой, не только первая. `mergeTask` проверяет не только итог слияния, но и каждый коммит, который оно приносит (`inspectHistory`: пути внутри `writePaths`, без секретных имён, симлинков и submodule, без известных секретов в содержимом, не больше 1000 коммитов); дефект откатывает слияние с кодом `project_integration_history`, попытка становится `blocked`. Пути и содержимое сравниваются по сырым данным Git (`rawOutput`, содержимое blob — байтами): редактирование вывода не может скрыть ни известный секрет формата ключа провайдера, ни секретное имя файла (`a&key=x/credentials.json`). Blob, который нельзя сравнить в пределах бюджета (`SECRET_SCAN_BYTES` = 16 МиБ на blob, `HISTORY_SCAN_BYTES` = 128 МиБ на проверку), блокирует слияние: `project_integration_history_unverifiable`.

`gateRepairInScope({worktree, from, to, writePaths})` — истина, если `to` (проверенный head gate Run) — потомок `from` (head гейта) и diff `from..to` лежит в `writePaths` покрытых задач. `mergeBackGate({worktree, expectedHead, gateHead})` возвращает проверенный head гейта (`gateHead = run.headSha`) в интеграционную ветку; `expectedHead = gate.headSha`. Если ветка всё ещё на `expectedHead` — fast-forward до `gateHead`; если её продвинули другие слияния — `--no-ff` слияние ремонтных коммитов (`Kodo: integrate gate repairs`). Уже слитый `gateHead` возвращает текущую голову. `gateHead` не потомок `expectedHead` или ветка без `expectedHead` — `project_integration_invalid`; конфликт — откат и `project_integration_conflict`. Вызывающий держит lease `project-integration:<id>`.

**`runtime/project-wave-evidence.mjs`.** `evaluateWaveTransition({command, snapshot, run, gate?, integrationHead?}, ports)` — чистый evaluator волновых переходов с результатом той же формы, что `evaluateProjectTransition`. Run задачи доводит attempt/task максимум до `integrated`: квитанция `task-fast` на голове Run, behaviour gate на том же head, `integration.status = merged` с `mergedHead = run.headSha`, ref `checks`. `accepted` задач и контейнеров даёт только текущий gate Run:

- гейт installed и не заменён, binding Run байт-в-байт равен `gateBindingFor(gate)` и хранит исходный `gate.headSha`; диапазон непустой (`gate.baseSha ≠ gate.headSha`, `run.headSha ≠ gate.baseSha`, `run.baseSha = gate.baseSha`); `run.headSha` — проверенный итоговый head (сам `gate.headSha` или его потомок после ремонта; Git-сверку потомка и writePaths делает доверенный `validateRun`), иначе `wave_gate_missing`;
- гейт G вытеснен для контейнера C, только если есть более новый гейт, тоже содержащий C (`wave_gate_superseded`). Для задачи C — её эпик, для контейнера — он сам: гейт `[B, M]` не вытесняет `[A, M]` для эпика A и его задач;
- `gate.merges` указывают на текущие попытки (`wave_merges_mismatch`);
- gate Run `succeeded`, полные checks без маркера профиля, ревью (его `diffHash` — не хэш пустого diff), behaviour receipt и включённые гейты — все на `run.headSha`; smoke на `run.headSha`, `complete`, `configured` ⇔ `config.commands.smoke` не пуст, ровно одна строка на каждую команду smoke в том же порядке с тем же `command`/`args`, exit 0 и журналом (`evidence` с `headSha = run.headSha`, `outputPath`/`outputHash`); refs — gate Run на `run.headSha`. Иначе `wave_gate_proof_missing`.

Правило голов: приёмка задач и эпика относится к проверенному head гейта. Приёмка **проекта** дополнительно требует `integrationHead === run.headSha`, где `integrationHead` — голова `refs/heads/kodo/project/<id>`, прочитанная доверенным вызывающим на момент приёмки (иначе `wave_project_head_mismatch`). Итоговый продукт всегда проверен целиком: если ветка ушла дальше проверенной головы, нужен гейт проекта на её текущей голове (drain резервирует его сам, см. «Исполнение»). Контейнер переходит в состояние S, когда все его дети уже в S. `released` в волновом режиме не поддерживается. Блокеры: `wave_not_enabled`, `wave_fast_proof_missing`, `wave_integration_missing`, `wave_gate_missing`, `wave_gate_superseded`, `wave_merges_mismatch`, `wave_gate_proof_missing`, `wave_dependency_unaccepted`, `wave_project_head_mismatch`.

**Авторизатор и директор.** `createProjectTransitionAuthorizer` маршрутизирует по `isWaveProject(snapshot.project)`: wave → `evaluateWaveTransition` (инжектированный `evaluator.evaluateWaveTransition`, иначе модуль), остальное — прежний путь без изменений. Для wave Run выбирается так: `task → ready` — без Run; `accepted` — единственный гейт снапшота, чей `runId` назван в `evidence`, и его Run (иначе `project_binding_invalid`), для `project` ещё и `integrationHead` из Git; attempt/task до `integrated` — Run текущей попытки; контейнеры до `integrated` — без Run. Доверенный `validateRun` wave (`validateWaveRun`, единственный для нативных задач, задач внешних чатов и гейтов): Run совпадает с сохранённым, binding (задачи — как в legacy; гейта — `gateBindingFor` + `buildGateInput`), root/config, чистый head. У задачи ещё `verificationProfile: 'task-fast'`; пока Run не `succeeded` (внешний чат ещё работает), этим проверка и ограничена, и evaluator даёт не больше `running`/`verifying`; у `succeeded` — журналы `fast-check` каждой строки, счёт каждой строки `node --test`, пересчитанный по файлу событий журнала (`testEvents`, текущий `countVersion`; расхождение — `project_fast_tests_uncounted`, см. [VERIFICATION.md](VERIFICATION.md)) и, если слияние записано, Git-сверка (`mergeOnBranch`): merge-коммит достижим из **текущей** головы `kodo/project/<id>`, у него ровно два родителя — `integration.before` и `run.headSha`. Сохранённой квитанции мало: после отката слияния или с чужим первым родителем `integrated` не записывается. У гейта — полные checks/ревью/гейты как в legacy, журналы `smoke`, `gateRepairInScope(gate.headSha → run.headSha)` (порт бросает `project_gate_scope`, evaluator даёт `trusted_proof_invalid`), манифест (`assertGateManifest`: артефакт цел, лежит в evidence gate Run, на `gate.headSha` и равен `buildGateManifest` покрытых задач, хэш которого связан с `run.task`; иначе `project_gate_manifest_invalid`), непустой диапазон (`gateRange` на `gate.headSha` и `git diff gate.baseSha run.headSha` не пуст, иначе `project_gate_range_invalid`) и сверка с веткой сейчас: каждое покрытое слияние — на first-parent истории текущей головы ветки с записанными родителями его Run задачи, `run.headSha` в ветке (`project_integration_invalid`; директор сначала делает `mergeBackGate`).

**Lease до фиксации.** Доказательство, которое читает интеграционную ветку — attempt/task → `integrated` и любой `accepted`, — проверяется под lease `project-integration:<id>` (`runtime/project-integration-lease.mjs`), и вызывающий держит его, пока Store не зафиксирует переход: `repo.apply` вызывается внутри `withIntegrationLease(store, projectId, work)`. Lease реентерабелен и передаётся по асинхронному контексту (`AsyncLocalStorage`); авторизатор проверяет `integrationLeaseHeld(store, projectId)` до и после проверок, иначе `project_integration_lease_required`. Так ни слияние, ни `mergeBackGate` Kodo не сдвинут ветку между Git-проверкой и записью. Для приёмки проекта голова ветки читается до проверок и ещё раз после них; при расхождении — `project_integration_head_changed`. Этим путём идут `drain`, `resume` (это `drain`) и `complete-task` (оба через `integrateAndAdvance` и `runPendingGates`). Ref приёмки контейнера сверяется с собственным наблюдением gate Run точно (`project-acceptance` гейта и есть доказательство контейнера); наблюдение Run задачи до контейнера не доходит. `run` wave-проекта отказывает кодом `project_wave_drain_required` без старта Run; `resume` — это `drain` одной волны (см. ниже).

**Профили проверки.** Задача волны проходит `task-fast` (затронутые тесты, behaviour gate, без гейтов и LLM-ревью), эпик — один gate Run с полной проверкой, smoke и ревью: [VERIFICATION.md](VERIFICATION.md). Исполнение волн описано в следующем разделе; внешние воркер-чаты T3 — [T3-HOST.md](T3-HOST.md).

## Волновой режим: исполнение (drain)

`kodo project drain PROJECT_ID` исполняет wave-проект до приёмки или остановки: по умолчанию до 10 волн по 3 задачи (`--max-waves 1..100`, `--concurrency 1..5`). Аргументы разбираются строго, до чтения credentials и state. Exit0 — `accepted` или `max_waves`, exit1 — неверный ввод, exit2 — остальные статусы и ошибки, в том числе legacy-проект (`project_wave_not_enabled`). `--command-id` относится к первой резервации, как у `resume`.

Цикл `drain` (`runtime/project-director-waves.mjs`) идёт под lease `project:<id>` с опросом отмены, как `resume`:

1. **Восстановление.** Открытые нативные попытки после сбоя или квоты продолжают тот же Run; завершённый Run только интегрируется. Нативность решает `attemptExecutor`: у установленного Run — его `executor`, у резерва без Run (сбой между `reserveAttempt` и установкой) — actor события резерва (`project-director` у drain, `project-external:<host>` у pull-хоста). Попытки внешних чатов и резервы чужого владельца drain не исполняет и не подхватывает: их writePaths только заняты. С `--retry-failed` для задач с blocked/failed/cancelled попыткой резервируется по одной новой попытке: не больше `concurrency` и без пересечения writePaths. Повтор идёт тем же исполнителем, что и прошлая попытка: drain повторяет только свои нативные попытки; задачу, брошенную внешним чатом, он не исполняет (блокер `wave_retry_executor`), её повторяет `next-wave --retry-failed` того же хоста.
2. **Гейты.** `runPendingGates` запускает гейт эпика, когда все его задачи integrated, а их зависимости вне эпика accepted; затем, если остался только проект, — гейт проекта (ниже).
3. **Волна.** `selectWave` берёт задачи горизонта планировщика без пересечения writePaths (`scopesOverlap`) между собой и с задачами внешних чатов. Для каждой задачи: task → ready, `reserveAttempt` и Run от головы интеграционной ветки (`waveFrontier`). Run получает `verificationProfile: 'task-fast'`, режим quick без research и Gemini, выключенную доставку, `config.watchdog` из `execution.watchdog` или `{stalledRounds: 2, rejectUnchanged: true}` и `config.concurrency` из `--concurrency`. Worktree создаются по одному, затем `Engine.run` всех задач волны идёт параллельно. Завершившиеся задачи интегрируются по одной. Запись узла задачи вне её writePaths (`checkScope`, `scope_conflict`) сразу останавливает Run задачи с блокером `scope_conflict`: раунд ремонта на неё не тратится, в итоге `drain` — `blockers: [{code: 'scope_conflict', kind: 'task', id}]`. Это правило только профиля `task-fast` (Run задач волны); обычный Run повторяет узел в пределах `repairRounds`, как прежде.
4. После волны снова идут гейты, затем следующая волна.

**Интеграция** (`integrateAndAdvance`) выполняется под lease `project-integration:<id>`. Голова Run сливается в `kodo/project/<id>`, `run.integration` переходит из `pending` в `merged`. Директор сохраняет evidence `acceptance`, `contract` и `checks` Run задачи и проводит attempt и task до `integrated`. Контейнер доходит до integrated, когда там все его дети. Повтор после сбоя восстанавливает записанное или уже сделанное слияние, второго merge-коммита нет. Во всех ветках повтора (слияние записано в Run, или attempt и task уже `integrated`) под lease сверяется, что записанный merge-коммит достижим из головы ветки и его родители — `before` и голова Run (`mergeOnBranch`); расхождение (ветку откатили или переписали) — `blocked`, `project_integration_missing`, не `integrated`. Конфликт или выход за writePaths переводит попытку в blocked; дальше нужен `--retry-failed`, новая попытка начинается от текущей головы ветки. До слияния проверяется политика проверок задачи (`wave_policy_mismatch`, если Run проверен не политикой своей базы или голова меняет `kodo.config.json` вне `writePaths`).

**Гейт эпика.** Контейнеры: эпик; milestone, если остальные его эпики приняты; project, если приняты все остальные эпики проекта. `merges` — текущие попытки задач самого широкого контейнера в порядке задач снапшота. Ремонтные коммиты гейта проверяются так же, как коммиты задачи: перед `mergeBackGate` под lease `inspectHistory` проходит весь диапазон `gate.headSha..run.headSha` по `writePaths` покрытых задач; дефект (секретный файл, добавленный и удалённый ремонтом, путь вне `writePaths`, известный секрет) не сливается, gate Run становится `blocked` с `project_integration_history` (или `..._unverifiable`), а `--retry-failed` резервирует новый гейт. Head — голова ветки, база — `gateBase`: первый родитель самого раннего покрытого merge-коммита на first-parent истории головы, так что ревью и behaviour gate видят diff всех покрытых слияний. Резерв (`reserveGate`) и установка gate Run (`createGateRunDraft` → `repo.installGateRun`) идут под одним lease `project-integration:<id>`, поэтому гейт всегда стартует с зарезервированной головы. Резерв, установка которого прервалась, ставится при следующем проходе; если голова ветки за это время ушла (`gate_head_stale`), drain резервирует новый гейт на текущей голове, а прежний помечается `supersededBy` и уже не ставится. Точный повтор установки уже установленного гейта возвращает его Run до проверки головы. После успешного gate Run под тем же lease, удерживаемым до фиксации каждой приёмки, проверенный head возвращается в ветку: `mergeBackGate({expectedHead: gate.headSha, gateHead: run.headSha})` — fast-forward, пока ветка стоит на голове гейта, иначе `--no-ff` «Kodo: integrate gate repairs». Ремонт внутри гейта приёмке не мешает. Директор сохраняет evidence `acceptance`, `contract`, `checks` и `review` гейта. Затем задачи (attempt и task), эпик и покрытые milestone и project переходят в accepted; проект — только пока голова ветки равна проверенному head гейта. Неудачный гейт повторяется только с `--retry-failed`: резервируется новый гейт с `retry: true`. В quick-режиме gate Run получает не меньше двух раундов ремонта (`repairRounds = max(2, профиль)`), иначе ремонт не перепроверяется. Политика проверок гейта — из `kodo.config.json` его головы (`gate.headSha`), поэтому оракулы и `commands.smoke`, добавленные задачами эпика, исполняются гейтом; падающий оракул оставляет эпик и проект непринятыми. Задача же проверяется политикой коммита своей базы ([VERIFICATION.md](VERIFICATION.md#политика-проверок-волнового-run)).

**Гейт проекта.** Если все milestone приняты, а проект нет — ветка ушла дальше проверенной головы гейта, покрывшего проект (например, сдвиг во время гейта эпика или во время проверки приёмки), — `runPendingGates` резервирует гейт `[project]` на текущей голове ветки: merges всех задач, база — первый родитель самого раннего слияния, то есть ревью всего проекта. После успеха он принимает проект. Если ветка снова ушла во время этого гейта, в том же проходе резервируется ещё один (Store разрешает новый гейт проекта при `succeeded` прежнем с другой головой); после второго подряд — блокер `wave_project_head_mismatch`.

Результат: `{status, waves, integrated, gates: [{gateId, runId, state}], blockers: [{code, kind, id}], revision, code?}`.

| `status` | Когда |
| --- | --- |
| `accepted` | Проект принят |
| `max_waves` | Выполнено `--max-waves` волн |
| `waiting_limits` | Квота Run задачи или гейта; следующий `drain` продолжает тот же Run |
| `blocked` | `code`: блокер Run или сторожа (например, `no_verified_progress`), `project_integration_conflict`, `risk_approval_required`, если горизонт закрыт только risk approval, иначе первый блокер |
| `paused` | Активные Run доходят до конца, интеграция ждёт следующего запуска |
| `cancelled` | Проект отменён |

`resume` волнового проекта — это `drain` с `maxWaves: 1` и `concurrency: 1`: ровно одна задача (или продолжение одной открытой попытки) и гейты, которые она открыла. `status: succeeded` при `accepted` или `max_waves`, исходный статус — в `drainStatus`. `cancel` также ставит `cancelRequested` незавершённым gate Run. `released` для волнового проекта не поддерживается: `project_wave_delivery_unsupported`.

Внешние воркер-чаты (pull-хост T3/Orca, [T3-HOST.md](T3-HOST.md)) используют те же функции (`selectWave`, `integrateAndAdvance`, `runPendingGates`, `integrationOf`) и тот же авторизатор. `drain`, `next-wave` и `complete-task` держат один lease `project:<id>`: одновременно с идущим `drain` pull-команды отвечают `project_busy`.

Ограничения:

- Lease `project-integration:<id>` защищает только от записей Kodo. Ручное изменение ветки пользователем во время приёмки ловят повторные Git-проверки авторизатора (для проекта — повторное чтение головы), но не lease.
- Содержимое отката слияния через `git revert -m 1` (merge-коммит остаётся в истории) Git-сверка не видит; это ловит следующий гейт.
- Гейт проекта повторяется в одном проходе не больше двух раз подряд.

Проверка: `tests/project-wave-director.test.mjs` (реальный Engine с fake-провайдерами, временный Git; lease и откат слияния, сдвиг головы при приёмке, гейт проекта, замена устаревшего резерва), `tests/project-wave-large-gate.test.mjs` (240 задач, 24 эпика), `tests/project-wave-cli.test.mjs` и сквозной `tests/project-wave-e2e.test.mjs` (drain двух эпиков с ремонтом в гейте, T3-путь, владение резервом и повтором; без fake-портов).

## Lifecycle и текущие ограничения

`proposed → ready → running → verifying → integrated → accepted → released`, плюс blocked/failed/cancelled; Attempt начинается с reserved. Ни текст «completed», ни `verified:true`, ни переданные `eligibleStates` не заменяют trusted authorizer. Он await-ит доказательства до write transaction; Store повторяет CAS/control/binding checks внутри неё, без await. Safety проверяет декодированные ключи и значения до hash/write/output, включая короткие known values, PEM и изменения от redaction; ошибки не раскрывают совпавший секрет.

Accepted требует exact frozen task, фактические checks и независимый review текущего clean head, criterion mappings и свежие enabled gates. Disabled — neutral. Released дополнительно требует проверенную publication chain; Project release требует released у `releaseRequired` milestones. Accepted history не понижается.

Epic/Milestone/Project требуют полный набор принятых children **и собственные** criterion evidence/mappings. Автоматическая Task success observation не является собственным proof контейнера. В текущем CLI нет ввода/amend evidence и mappings контейнера или произвольных backlog edits; это trusted repository integration. Поэтому даже все принятые Task могут оставить `resume` blocked (`own_proof_missing`, неоднозначный bound Run и другие причины). Шаблоны ниже не обходят эту границу и не обещают end-to-end project acceptance. К волновым проектам это не относится: их контейнеры принимает gate Run, evidence которого и есть собственное доказательство контейнера.

`resume` — явная foreground команда: обрабатывает одну Task/Attempt через существующий Engine и возвращается; не постоянный daemon и не drain-loop всего backlog. Для волнового проекта `resume` и `drain` описаны в разделе «Волновой режим: исполнение». Единственная project lease не допускает второго foreground controller. Restart/quota возобновляют ту же reservation/Run с прежними sessions и limits; `--retry-failed` явно создаёт следующую попытку для blocked/failed/cancelled Attempt, сохраняя историю. Это не `--retry-failed` цикла legacy Run. Несколько retry candidates требуют разрешения неоднозначности; отменённый Project не возобновляется.

`pause` сохраняет флаг и блокирует следующие starts/advancement, сохраняя уже активный Run/session; `resume` снимает pause. `cancel` сначала сохраняет Project как cancelled, переводит активные Attempts в cancelled и устанавливает `cancelRequested` связанного Run до передачи отмены Engine. Исторические blocked/failed/cancelled Attempts сохраняют статус, Task revision, contractHash и evidence даже после reprioritize Task; accepted/released не затрагиваются. Повторный cancel, включая повтор после открытия SQLite, возвращает cancelled и повторно передаёт отмену связанного Run без переписывания terminal history. Явная отмена/потеря lease/abort сохраняют cancellation semantics. Sophisticated prioritization UI, daemon, generic framework и автоматический container evidence importer отложены.
