# Kodo

Kodo объединяет каталог навыков и локальный исполнитель задач для Codex и Claude Code. Процесс начинается с ранней оценки Jev: **выбор режима → подходящий анализ → план основной модели → реализация с проверками → независимое ревью → настроенная доставка**. Для небольшой локальной задачи `quick` пропускает Gemini и исследование, объединяет код, проверки и нужную документацию в одном задании разработчику.

Нужен Node.js 24. GPT и Claude запускаются через установленные официальные клиенты и активные подписки. Отдельные API GPT/Claude не используются. Gemini, Jev и исследовательские сервисы используют свои ключи. [Репозиторий Kodo](https://github.com/Zulut30/Kodo).

## Установка CLI

Пакет распространяется через [GitHub Release 0.2.1](https://github.com/Zulut30/Kodo/releases/tag/v0.2.1), без публикации в npm:

```powershell
npm install -g "https://github.com/Zulut30/Kodo/releases/download/v0.2.1/zulut30-kodo-0.2.1.tgz"
kodo init
kodo doctor --json
```

`kodo init` включает [все 13 стандартных навыков](docs/DEFAULT-SKILLS.md) для Codex, Claude Code и OpenCode. Они также входят во все пресеты. Движок рассматривает их на каждом этапе; React/Next.js и monorepo-рекомендации применяются к соответствующим проектам.

## Запуск из исходников

```powershell
npm install
node cli/index.mjs init
node cli/index.mjs doctor --json
node cli/index.mjs run "Добавь поиск в каталоге компонентов" --client codex
```

Команду `node cli/index.mjs` можно заменить на `kodo` после установки CLI-пакета. Запускай её в целевом проекте или укажи `--project <путь>`. Проект должен быть Git-репозиторием с исходным commit. Его незакоммиченные изменения сохраняются: исполнители работают в отдельных worktree.

По умолчанию запуск использует модели одного клиента. Явно разрешить обе подписки:

```powershell
kodo run "Добавь экспорт в CSV и проверь его" --client claude-code --providers both
```

Состояние сохраняется между запусками:

```powershell
kodo status <runId> --json
kodo logs <runId>
kodo resume <runId>
kodo cancel <runId>
```

`doctor` проверяет локальные предпосылки. `doctor --live` выполняет отдельные реальные проверки провайдеров; такие обращения могут расходовать квоты подписок и API. Обычные тесты Kodo не обращаются к платным сервисам.

## Режимы и скорость

Без явного выбора Jev оценивает сложность, риск и область задачи до дорогого анализа. Уверенная локальная задача получает `quick`, высокая сложность/риск или сквозная область — `deep`, неопределённость и недоступный Jev — `standard`. Публичных режимов три; автоматический выбор означает отсутствие `--mode` и проектного `executionMode`.

| Режим | Gemini | Предел research-запросов | Предел задач плана | Бюджет попыток ремонта | Рабочая конкурентность |
| --- | --- | --- | --- | --- | --- |
| `quick` | Нет | 0 | 2; рекомендуется одно задание | 1 | 1 |
| `standard` | Да | 10 | 12 | 3 | 2 |
| `deep` | Да | 40 | 24 | 5 | 2 |

Меньшие проектные бюджеты сохраняются. Явный режим имеет приоритет над автоматической оценкой и проектной настройкой; `--model` фиксирует модель для планирования, реализации, ревью и повторов:

```powershell
node cli/index.mjs run "Исправь цвет обычной кнопки в src/button.css, сохрани остальные состояния" --client codex --mode quick --model gpt-6.1-sol
```

`quick` использует одну выбранную модель без отдельной маршрутизации каждого узла, реальные настроенные test/build, включённые UI/security gates и свежее независимое ревью. Это уменьшает объём оркестрации; время ответа модели не гарантируется. Режим фиксируется в запуске: `resume` его не меняет, автоматического повышения режима нет. Для расширения бюджета нужен новый запуск. [Точный контракт и восстановление](docs/RUNTIME.md#режимы-исполнения).

Парное сравнение Kodo с обычным native-клиентом:

```powershell
node cli/index.mjs benchmark run --client codex --models gpt-6.1-sol,gpt-6-astra,gpt-6.1-terra --mode quick --repeats 2 --seed 1 --output "D:\KodoBenchmarks\quick-pilot" --json
node cli/index.mjs benchmark report "D:\KodoBenchmarks\quick-pilot" --json
```

Это команды для реального прогона через подписку, а не опубликованные результаты. Бенчмарки отложены пользователем ради MVP; частичный пилот остановлен после 9 из 24 испытаний, данные сохранены для будущего продолжения. Выводов об ускорении и лучшей модели нет. Отчёт различает общее время, длительность native-сессий, правильность и соблюдение scope; неизвестные HTTP-счётчики и usage остаются `null`, точная стоимость подписки не рассчитывается. [Методика, resume и ограничения](docs/BENCHMARK.md).

Текущее дерево также использует непрерывную очередь: зависимый узел может стартовать сразу после интеграции своего предшественника, пока независимый worker ещё работает. Сохраняются отдельные worktree, решения Jev о последовательности, непересекающиеся scopes и лимиты подписок. Компактный контекст содержит обязательные требования и ссылки на полные приватные evidence; все 13 skill decisions и проверки pinned resources сохраняются.

На одинаковых локальных входах отдельные policy-контексты сократились на 51,74–59,36%, inline plan/review evidence — на 89,15%/91,79%, вывод managed RTK для Git log — на 63,65%. Это размеры частей данных в UTF-8, без модельных вызовов при измерении; они не показывают ускорение всей задачи или экономию квоты подписки. [Поведение, полные числа и ограничения](docs/EFFICIENCY.md).

## Необязательные инструменты и проверки

Текущее дерево содержит управляемые pins шестнадцати инструментов: Agent Desktop, Browser Use, Browser Harness, Vibetest, Jev Ultrafast, Chrome DevTools MCP, Semgrep, Gitleaks, ripgrep, RTK OSS 1.1.0, Oxlint 1.91.0, Oxfmt 0.76.0, TypeScript (tsc) 7.0.2, Stylelint 18.0.0, HTML-Validate 11.18.0 и SQLFluff 4.5.0. Шесть инструментов качества используют тот же изолированный installer с проверкой pins и версий; SQLFluff требует явного dialect при проверке проекта. Шесть UI-адаптеров выполняют реальные действия в собственном приложении/браузере и проверяют результат через независимый DOM/accessibility readback. Security gates запускают локальные сканеры. Установка хранится вне Git и не меняет глобальные инструменты.

RTK доступен явно для поддерживаемого человекочитаемого вывода в private worker environment; missing/unsupported использует исходные команды. JSON/protocol/porcelain/NUL, Node/TAP, полный check, CI и доставка остаются сырыми. Глобальный RTK 0.50.0 и hooks не меняются. [Правила RTK](docs/UI-TOOLS.md#rtk-и-вывод-shell).

```powershell
node cli/index.mjs tools list --json
node cli/index.mjs tools install browser-harness --json
node cli/index.mjs tools doctor --json
node cli/index.mjs ui verify --project "D:\Projects\my-app" --json
node cli/index.mjs security verify --project "D:\Projects\my-app" --json
```

У старых проектов UI/security по умолчанию выключены; в конфигурации самого Kodo включены Semgrep/Gitleaks, UI выключен как неприменимый к CLI. `disabled` сохраняется как `passed:null`. Включённые проверки выполняет координатор после build/test и до review/delivery, с привязкой к head/config/pins и приватным evidence. `tools doctor --live` проверяет только локальные версии/import metadata, без модели или UI. [Pins, лицензии, setup, JSON и границы](docs/UI-TOOLS.md), [реальные квитанции и проверки](docs/VALIDATION.md#интеграция-ui-security-и-контекста). Наличие реализации в checkout не подтверждает её публикацию в выпуске 0.2.1.

Для работы в desktop host сохраняй постоянный чат `Kodo · Диспетчер задач`. Координатор поручает реальную работу понятно названным видимым чатам через доступные app tools и после проверки архивирует только собственные завершённые worker-чаты. Диспетчер остаётся активным. CLI-native сессии сохраняются отдельно и автоматически видимыми чатами не становятся; универсальный desktop backend в CLI не заявляется. [Контракт чат-входа](skills/kodo-build-feature/SKILL.md).

## Аудит сохранённого запуска

Текущая реализация добавляет `kodo audit RUN_ID [--json]`. Для установленного CLI с поддержкой команды:

```powershell
$runId = "идентификатор-сохранённого-запуска"
kodo audit $runId
kodo audit $runId --json
```

Из текущих исходников: `node cli/index.mjs audit $runId --json`. Указанный выше выпуск 0.2.1 остаётся историей установки; наличие новой команды в опубликованном пакете подтверждается отдельно при выпуске.

Аудит читает только локальное состояние: `init`, конфигурация проекта, ключи, авторизация клиентов и Git не нужны. Текст показывает запуск, состояние, отсутствующие и некорректные этапы, число и список применимых навыков, сохранённые PR и релиз; JSON содержит ограниченный набор полей схемы 1.

Уровень доказательств — `recorded-instructions`: проверяется запись политики, а семантическое соблюдение инструкций моделью не доказано. `skills.complete` не означает успешные тесты или выпуск. Старый или незавершённый запуск доступен с `complete: false` и кодом выхода 0; неизвестный ID или неверные аргументы дают ошибку. [Схема, примеры и ограничения](docs/RUNTIME.md#аудит-сохранённого-запуска), [проверки](docs/VALIDATION.md#целевые-проверки-аудита).

## Запуск из чата

Установи навык в проект:

```powershell
node cli/index.mjs install skills/kodo-build-feature --client codex --client claude-code --target "D:\Projects\my-app"
```

Затем попроси: «Используй kodo-build-feature: добавь экспорт в CSV». Навык получает анализ через Kodo, а план составляет текущая основная модель чата. После передачи плана тот же движок выполняет задачу и отслеживает проверки и доставку. Формулировка «используй обе подписки» включает общий пул моделей.

OpenCode может загрузить тот же навык и передать выполнение настроенному backend Codex или Claude Code. Собственный backend дешёвых моделей OpenCode относится к будущему этапу.

## Каталог компонентов

```powershell
kodo list
kodo list --search "архитектура" --json
kodo registry stats --json
kodo show skills/code-review
kodo plan pipelines/fix-bug
kodo init --preset nextjs --client all --target "D:\Projects\my-app" --dry-run
```

| Раздел | Назначение |
| --- | --- |
| `skills/` | Проверка кода, UI, SEO, диагностика и вход в исполняемый процесс Kodo |
| `pipelines/` | Последовательности работы и ожидаемые результаты |
| `agents/` | Архитектор, разработчик, дизайнер, QA и документирование |
| `mcp/` | Шаблоны GitHub, Playwright, опционального Chrome DevTools MCP и Supabase для клиентов |
| `presets/` | Комплекты инструкций Next.js, .NET и WordPress |
| `adapters/` | Пути и форматы компонентов для каждого клиента |
| `runtime/` | Состояние, провайдеры, рабочие сессии и доставка |
| `registry.json` | Компоненты и их зависимости |

Установка пресета копирует инструкции и шаблоны; запуск через `run` выполняет рабочий процесс. Инструкции проекта из `AGENTS.md` и `CLAUDE.md` продолжают действовать.

## Состояние и доставка

Компоненты установки хранятся в `.kodo/components/`, а lock содержит версии и SHA-256 управляемых файлов. Установщик отказывается перезаписывать чужой или изменённый файл. `--dry-run` проверяет план без записи. [Переход со старой установки](docs/MIGRATION.md).

Ключи и состояние запусков находятся в отдельных пользовательских каталогах вне Git. Ключи защищаются Windows DPAPI или Unix-правами `0600`; в проекте хранится `kodo.config.json` без ключей. Рабочим агентам ключи не передаются, но выполнение кода тем же пользователем требует доверия. [Хранение и границы доверия](docs/SECURITY.md).

Перед merge нужны успешные актуальные проверки и независимое ревью. Выпуск привязывается к конкретному commit. Для Kodo результатом выпуска служат GitHub Release, `.tgz`, SHA-256 и проверка установленной команды; публикации в npm нет. Успех реализации, тестов, merge и выпуска отражается раздельно.

MCP-шаблоны лежат в `.kodo/components/mcp/<name>/`. Они не подключаются автоматически: выбранный сервер настраивается по приложенному README.
